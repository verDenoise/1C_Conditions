## Базовая мысль - код обязан быть структурирован

И минимальной структурированной единицей кода являются именованные объекты, имена которых тоже должны подчиняться правилам и законам.

Текущая проблема в том, что естественное написание на русском языке не предполагает каких-то четких правил. И порождаемый таким естественным написанием код сложно структурируется естественным путем - базовые вещи (имена) разнородны и бессистемны.

Предлагается ввести правила и систему стиля ООП в базовое именование, что естественным путем порождает хорошие кодовые структуры верхнего уровня.

## Решаемые проблемы

1. Некорректное размещение кода / смешивание различного функционала в одном модуле.
  > Например ```ЗапасыСервер``` из ERP - размещено все. и пользовательский интерфейс и запросы и проведение и проверки и ....
2. Мегамодули.
  > Как следствие из 1. Типовой емкий модуль это 10000+ строк кода, что усложняет понимание, поддержку и при разработке часто дает конфликты блокировок модулей.
3. Дублирование кода.
  > 
* Отсутствие библиотек кода как результата разработки / постоянные велосипеды
* Отсутствие правил именований -> разномастные имена модулей/методов
* Отсутствие критеерия оценки имен -> допустимо фактически любое

## Профит при использование

* Отсутствие "Мегамодулей"

  > Обычная проблема в 1С -

* Отсутствие дублирования кода
* Библиотеки кода как естественный результа+т кодирования
  > Как следствие из библиотек - раздельный контроль за объемами тех. долга, лучший контроль за качество кода
* Отсутствие смешивания функционала
* Критерии оценки корректности имен объектов
* Единый принцип именования -> единый стиль


Первичные договоренности, на что проверяем - в новом варианте называем в стиле ООП, чтобы при наличии точек перед заглавными буквами получалась осмысленная конструкция вида ```Объект.Свойство.Метод()```. Про переменные дальше, но там беды примерно те же. Четко понимаем, что имя метода должно в явном безусловном виде совпадать с тем, что он делает

Пример разницы на примере ОМ.ЗапасыСервер из ЕРП. После комментария нормализованное имя

```bsl

ТекстЗапроса = ЗапасыСервер.ТекстыЗапросовСторнирования(МетаданныеДокумента); // Запасы.Сервер.Запрос.Текст.Сторнирование()

ЗапасыСервер.ЗаписатьДанные(ТаблицыДляДвижений, Документ, Отказ); // Запасы.Сервер.Данные.Записать()
ЗапасыСервер.ПередЗаписьюДвиженийДокумента(Документ, МенеджерВременныхТаблиц, Отказ); // Запасы.Сервер[.Событие].Документ.Движения.ПередЗаписью()
ЗапасыСервер.ИнициализироватьДанныеКонтроляИзменений(Запрос, ТекстыЗапроса, Документ); // Запасы.Сервер.Контроль.Данные.Инициализировать()

Значение = ЗапасыСервер.ПроверитьИзменениеРеквизитовДокумента(МенеджерВременныхТаблиц, Ссылка, ИменаРеквизитов); // Запасы.Сервер.Документ.Реквизиты.Изменение.Проверить()
```

Основные претензии к текущей ситуации

1. Смешивание различного функционала в одном модуле - потому что имена бессистемные, вроде все по-русски и нормально
2. Длинный код - неудачные имена порождают неудачные реализации потому что по имени методы делают все и сразу
3. Как следствие сложность чтения и управления
4. Гавно параметры от недопонимания что на самом деле передается - передаются неуправляемые структуры. Что они такое, как с ними работать вообще непонятно пока не прочитает страницу/другую кода

### Проблема - плохие имена

##### ОблачныйАрхив.РазрешенаРаботаСОблачнымАрхивом

```bsl
#Область ФункциональныеОпции

// Можно ли технически работать с облачным архивом и включена ли опция, разрешающая работать с этой подсистемой.
// В отличие от ВозможнаРаботаСОблачнымАрхивом() проверяется наличие технической возможности
//  и результат выбора пользователя в форме настроек.
// Это результат функциональной опции "РазрешенаРаботаСОблачнымАрхивом",
//   И доступны нужные роли,
//   И это файловая база,
//   И конфигурация запущена в Windows,
//   И информационная база работает в локальном режиме,
//   И это не веб-клиент и не внешнее соединение.
// 
// Возвращаемое значение:
//  Булево - Истина, если возможна и разрешена работа с облачным архивом.
//
Функция РазрешенаРаботаСОблачнымАрхивом() Экспорт

// Вызов извне
ОблачныйАрхив.РазрешенаРаботаСОблачнымАрхивом
// Пробуем нормализовать
ОблачныйАрхив.Разрешена().Работа
ОблачныйАрхив.Работа.Разрешена() 
```
нормализовано ```bsl ОблачныйАрхив.Работа.Разрешена()``` - противоречие описанию. ключевое здесь выбор в настройках. то есть включена ли эта настройка (доступная по всяким там условиям)

*претензия* - типичное масло маслянное. ОблачныйАрхив...ОблачныйАрхив. Предпосылки - смешивание различного функционала в одном модуле. 

Подумаем, а что же это такое на самом деле? Читаем описание, ключевое слово в нем *настроек*. Это результат какой-то настройки, следовательно полное имя на самом деле это включен ли функционал где-то в настройках
```bsl
ОблачныйАрхив.Настройка.Включено()
// Сокращаем все точки кроме последней и получаем
ОблачныйАрхивНастройка.Включено()
```

##### ОблачныйАрхив.ВозможнаРаботаСОблачнымАрхивом
```bsl
// Можно ли технически работать с облачным архивом.
// В отличие от РазрешенаРаботаСОблачнымАрхивом() проверяется только наличие технической возможности работы с облачным архивом.
// Это результат, что
//   доступны нужные роли,
//   И это файловая база,
//   И конфигурация запущена в Windows,
//   И информационная база работает в локальном режиме,
//   И это не веб-клиент и не внешнее соединение.
// 
// Возвращаемое значение:
//  Булево - Истина, если возможна работа с облачным архивом.
//
Функция ВозможнаРаботаСОблачнымАрхивом() Экспорт

// Вызов извне
ОблачныйАрхив.ВозможнаРаботаСОблачнымАрхивом()
// нормализация
ОблачныйАрхив.Возможна().Работа
ОблачныйАрхив.Работа.Возможна()
// опять же работа, расшифровка ниже
```
нормализовано ```bsl ОблачныйАрхив.Работа.Возможна()``` - здесь прямого противоречия описанию нет, но слово Работа очеь общее, и требует перефразировки

*претензии* - масло маслянное. плюс наличие слова **Работа** в имени сразу же настораживает, оно в 99% случаев лишнее, название неудачное. Значит подобрали синоним, доступный со словом Работа, а в действительном написании название неудачное даже в естественном русском. Читаем описание, вывод - *на самом деле возвращается **Доступность** функционала в текущей среде выполнения (есть роли/платформа/...)*. Делаем вывод как должно быть
```bsl
ОблачныйАрхив.Подсистема.Доступна()
// нормализуем
ОблачныйАрхивПодсистема.Доступна()
```

##### ОблачныйАрхив.СобратьДанныеПоОблачномуАрхиву
```bsl
// Процедура выполняет обновления подсистемы Облачный архив.
// Процедура запускается как фоновое задание и собирает все необходимые данные
//  для панели администрирования БСП и формы настроек.
// Данные сохраняются в настройках, поэтому при успешном завершении, просто необходимо прочитать данные из настроек.
//
// Параметры:
//  ДополнительныеСвойства - Структура - произвольные дополнительные свойства. Может содержать:
//    * МассивШагов - Массив из Структура - массив структур со следующими ключами
//         (см. также ОблачныйАрхивКлиентСервер.ПолучитьОписаниеШагаСбораДанных()):
//      ** КодШага - Строка, возможные значения:
//        *** "ИнформацияОКлиенте";
//        *** "НастройкиАгентаКопированияКлиент";
//        *** "АктивацииАгентовКопирования";
//        *** "СвойстваХранилищаОблачногоАрхива";
//        *** "СписокРезервныхКопий";
//        *** "ДоступныеВерсииАгентаКопированияОблачногоАрхива".
//      ** ОписаниеШага - Строка;
//      ** СрокУстареванияСекунд - Число - число секунд, после которого считается, что данные устарели и их необходимо
//                                 собрать заново, если <= 0, то собирать данные принудительно;
//  АдресХранилища - Строка - Адрес временного хранилища. Нужно для вызова из общего модуля ДлительныеОперации.
//
Процедура СобратьДанныеПоОблачномуАрхиву(ДополнительныеСвойства, АдресХранилища = Неопределено) Экспорт

// нормализуем
ОблачныйАрхив.Собрать().Данные
ОблачныйАрхив.Данные.Собрать()

```
нормализовано ```bsl ОблачныйАрхив.Данные.Собрать()``` - прямое противоречие имени и типа метода, есть претензии по реализации. На самом деле ДопСвойства надо рассматривать как отдельный объект со всеми вытекающими. И нет прямого управления результатом. Ну и все такое 

*претензии* - масло маслянное это сразу, из названия вообще непонятно что тут делается. *Собрать* при этом *Процедура*. Понятно, что должен быть какой-то результат, но как его получить то? Из названий параметров понятно, что передается коллекция свойств сбора, но непонятно как этими свойствами управлять, что там лежит, какого типа, .... надо вчитываться, смотреть код. Адрес хранилища - что это такое - адрес куда надо складывать или возвратный параметр раз подразумевается результат? ОК. Вчитываемся в описание.... На самом деле *"выполняет обновление подсистемы"* прям первыми словами. Вчитываясь понимаем, что это обновление данных, получаемых извне. Вчитываясь еще и в код, понимаем, что это действительно пошаговое чтение внешних данных (возможно из внешнего сервиса и по-этому в фоне). При этом все шаги смешаны в одном методе и он он **какой длинный**. Что должно быть
```bsl
// основной метод, который вызывает все остальное
Процедура ОблачныйАрхив.Данные.Кэш.Обновить(Элементы, АдресХранилища = Null)
// и сбор данные в явном виде
Функция ОблачныйАрхив.Данные.Кэш.ИнформацияОКлиенте()
Функция ОблачныйАрхив.Данные.Кэш.НастройкиАгентаКопированияКлиент()
...
// и очень желательно какое-то управление параметрами шагов, что-то наподобии
ОблачныйАрхив.Данные.Элемент.НаборСоздать()
ОблачныйАрхив.Данные.Элемент.НаборУмолчание()
ОблачныйАрхив.Данные.Элемент.НаборДобавить(Элемент)
ОблачныйАрхив.Данные.Элемент.ИнформацияОКлиенте(СрокУстаревания = -1)
ОблачныйАрхив.Данные.Элемент.НастройкиАгентаКопированияКлиент(СрокУстаревания = -1)
...
```
разница - вместо одного метода на 8 экранов получаем + 2 модуля, в явном виде определяющий элементы и весь локальных кэш. Плюсом они содержат мелкие, содержащие только свое методы. Тут в общем и переиспользование и объявления в одном месте и все из стандартов в общем

### Проблема - магические константы

### Проблема - неверное размещение кода по областям и модулям
##### Пример тот же ОблачныйАрхив

Область ПрограммныйИнтерфейс говорит сам за себя, область СлужебныйПрограммныйИнтерфейс тоже. И они **НЕ могут быть смешаны в одном модуле** - иначе это крайне затрудняет работу с ним. Ведь без провала в модуль непонятно, чем можно пользоваться, а чем пользоваться нельзя. Бывает еще хуже, когда экспортные методы размещены в области СлужебныеПроцедурыИФункции (пример там же). 

Предпосылки - недопонимание смешение функционала, как следствие много разнопланового кода в одном месте и недопонимание что же на самом деле мы пишем. 

*Здесь должна быть таблица правил* - есть неправильное размещение не только в общих модулях, но и модулях менеджеров и в модулях объектов

### Проблема - потери времени
###### Как следствие из перечиленных проблем

**При написании кода** - несмотря на то, что в абсолютном выражении неструктурированный код пишется быстрее, но в относительном выражении значительно медленнее - меньше полезного кода на единицу наполнения. Потому что пишется много дублирующего кода. Предпосылки к этому - плохая структура существующих методов, вынужденное написание длинных методов, непонимание что где должно (может) находиться.

**При чтении кода** - вообще непонятно что делает код. Яркий пример - все со словом *Проверить* в типовых. И пока не провалишься не угадаешь

**При эксплуатации** - так как куча дублирующего кода, то далеко не факт, что по сути одна и та же функциональность одинаково правильно написана в разных местах.
