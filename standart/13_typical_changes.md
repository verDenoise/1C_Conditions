# 13. Изменение типовой конфигурации

[Оглавление](./README.md) | Назад: [12. Форматирование](./12_formatting.md) | Далее: [14. Расширения](./14_extensions.md)

## Правила

### 13.1 Общие правила

- **13.1.1** Изменения типовых объектов минимизируются. Любое изменение типового объекта имеет аргументированное обоснование.
- **13.1.2** Изменение типового кода или типовых реквизитов допускается в исключительных случаях и обязательно отражается в документации проекта.
- **13.1.3** Всё, что можно сделать расширением, делается расширением (см. [14. Расширения](./14_extensions.md)).
- **13.1.4** Новые хранимые данные (объекты и реквизиты) добавляются в конфигурацию.
- **13.1.5** Новые методы размещаются в нетиповых общих модулях. Добавлять методы в типовые общие модули запрещено.
- **13.1.6** При изменении типового модуля нельзя переформатировать его (менять отступы, добавлять пустые строки). Сравнение конфигураций должно показывать только реальные изменения. Правила [12. Форматирование](./12_formatting.md) применяются только к добавляемому коду внутри меток.
- **13.1.7** Копирование больших типовых фрагментов ради небольшой правки запрещено: копия запроса на 20+ строк ради изменения пары строк, копия типовой формы ради пары элементов. Вместо копирования вносятся точечные программные изменения.

### 13.2 Изменение типовых хранимых данных

- **13.2.1** Расширение типа значения типового реквизита — только по согласованию с архитектором.
- **13.2.2** Допустимо добавлять нетиповые поля в: планы обмена, справочники, **шапки** документов, **реквизиты** регистров, отчёты, обработки, планы видов характеристик, планы счетов, планы видов расчёта, бизнес-процессы, задачи.
- **13.2.3** Без прямого согласования с архитектором запрещено изменять:
  - состав аналитик табличных частей проводимых документов, особенно если он влияет на уникальность выборок для движений;
  - состав ресурсов регистров.
- **13.2.4** Изменять состав измерений регистров запрещено безусловно.

### 13.3 Метки изменений

- **13.3.1** Каждое изменение типового кода обрамляется меткой с номером задачи, именем пользователя хранилища и датой. Закрывающая метка повторяет номер задачи, пользователя и дату открывающей — так парные метки легко найти поиском. Метки вставляются [шаблонами текста](../templates/README.md).
- **13.3.2** Изменённый или удалённый типовой код не удаляется, а сохраняется закомментированным внутри метки. Это единственный случай, когда закомментированный код разрешён. Код комментируется стандартной командой конфигуратора (`//` без пробела), чтобы его было легко отличить от поясняющих комментариев.

| Метка | Когда |
|---|---|
| `[+]` | код добавлен |
| `[*]` | код изменён: исходный типовой код закомментирован, новый добавлен |
| `[-]` | код удалён: исходный типовой код закомментирован |

<details><summary>Примеры к 13.3</summary>

Добавление:

```bsl
// [+] #4521 ИвановИИ 2026-09-30 {
// Заполнение склада по умолчанию из настроек пользователя
пр_ЗаказКлиента.СкладПоУмолчаниюЗаполнить(ЭтотОбъект);
// } #4521 ИвановИИ 2026-09-30
```

Изменение:

```bsl
// [*] #4530 ИвановИИ 2026-09-30 {
// Цена берётся с учётом соглашения клиента
//Цена = ЦенообразованиеСервер.ЦенаНоменклатуры(Номенклатура, ВидЦены, Дата);
Цена = пр_Цена.ПоСоглашению(Номенклатура, Соглашение, Дата);
// } #4530 ИвановИИ 2026-09-30
```

Удаление:

```bsl
// [-] #4544 ИвановИИ 2026-09-30 {
// Проверка лимита перенесена в пр_ЗаказКлиентаЛимит
//ЛимитПроверить(Отказ);
// } #4544 ИвановИИ 2026-09-30
```

</details>

## Пояснения и рекомендации

### Почему в типовом коде нужны подписи и закомментированный код

В своём коде подписи «кто и когда изменил» и закомментированный код запрещены: историю хранит хранилище или Git. С типовым кодом ситуация другая. При обновлении конфигурации разработчик сравнивает и объединяет модули, и история хранилища в этот момент не поможет: нужно прямо в тексте видеть, что здесь наша доработка, зачем она сделана, по какой задаче и как выглядел исходный код. Метки дают ровно это.

### Минимум изменений — не главный критерий

Трудоёмкость будущих обновлений определяется не только количеством изменений. С одной стороны, изменений должно быть мало, чтобы при обновлении переносить меньше. С другой — перенос должен быть надёжным, а изменения — легко находиться при сравнении и объединении. Поэтому скопированный целиком типовой запрос с правкой в двух строках хуже, чем две точечные программные правки: при обновлении копия незаметно разойдётся с оригиналом.
