# 4. Методы

## Правила

### 4.1 Декомпозиция

- **4.1.1** Деление кода на методы продумывается заранее, до начала написания.
- **4.1.2** Метод делает то и только то, что обозначено в его имени.
- **4.1.3** Дублирование кода запрещено, в том числе дублирование кода коллег. Перед написанием кода поищите в проекте и в БСП готовую реализацию.
- **4.1.4** Длина метода — не больше 40–60 строк (один экран). Исключения, которые нужно обосновать: текст запроса, инициализация коллекции, программное создание элементов формы, условное оформление, обоснованно неделимый алгоритм.
- **4.1.5** Логические блоки внутри метода отделяются пустой строкой. Если метод длиннее 20 строк не делится на логические блоки, его стоит переписать. Часто каждый такой блок лучше выделить в отдельный метод.
- **4.1.6** В отдельный метод выделяется логически обособленная часть алгоритма, даже если она вызывается один раз или состоит из одной строки.
- **4.1.7** Вложенность вызовов в одном выражении — не больше двух. При большей вложенности добавьте промежуточную переменную.
- **4.1.8** Не создавайте лишних переменных. Лишняя — та, что используется один раз, хранит выражение не более чем с двумя операндами **и своим именем ничего не объясняет**. Переменная, которая даёт имя «магическому» значению (5.8) или поясняет смысл выражения вместо комментария (11.1.2), не лишняя.
- **4.1.9** В коде релиза нет неиспользуемых методов. Интерфейс общих механизмов, который пока никто не вызывает, допустим, но «мусорного» кода быть не должно.
- **4.1.10** В коде нет закомментированных фрагментов. Единственное исключение — изменение кода типовой конфигурации (см. [13. Изменение типовой конфигурации](./13_typical_changes.md)).

<details><summary>Примеры к 4.1</summary>

Вложенность вызовов:

```bsl
// ❌ Плохо: три уровня вложенности, выражение приходится разбирать изнутри наружу
Сумма = пр_Цена.ВВалюту(пр_Цена.СоСкидкой(пр_Номенклатура.ЦенаРозничная(Номенклатура), Скидка), Валюта);

// ✅ Хорошо
ЦенаРозничная = пр_Номенклатура.ЦенаРозничная(Номенклатура);
ЦенаСоСкидкой = пр_Цена.СоСкидкой(ЦенаРозничная, Скидка);
Сумма = пр_Цена.ВВалюту(ЦенаСоСкидкой, Валюта);
```

Лишняя переменная:

```bsl
// ❌ Плохо: переменная используется один раз и ничего не поясняет
ИмяРеквизита = "Склад";
Реквизиты.Добавить(ИмяРеквизита);

// ✅ Хорошо
Реквизиты.Добавить("Склад");

// ✅ Тоже хорошо: используется один раз, но имя объясняет число
ПлатежейВФайлеМаксимум = 1000;
ФайлыПлатежи = пр_ВыгрузкаБанк.ПлатежиРазбить(Платежи, ПлатежейВФайлеМаксимум);
```

Выделение логической части в метод, даже одностроковой:

```bsl
// ❌ Плохо: читателю приходится разбирать условие, чтобы понять его смысл
Если Заказ.Статус = Перечисления.СтатусыЗаказовКлиентов.Согласован
	И Заказ.ДатаОтгрузки <= ТекущаяДатаСеанса() Тогда

	пр_Отгрузка.Создать(Заказ);

КонецЕсли;

// ✅ Хорошо: смысл условия выражен именем функции
Если пр_ЗаказКлиента.ОтгрузкаДоступна(Заказ) Тогда
	пр_Отгрузка.Создать(Заказ);
КонецЕсли;
```

</details>

### 4.2 Параметры

- **4.2.1** Параметры идут в порядке важности. Параметры со значениями по умолчанию — последние.
- **4.2.2** Параметры методов, которые вызываются со сменой контекста (с клиента на сервер), объявляются с модификатором `Знач`. Так изменённые значения не передаются обратно на клиент.
- **4.2.3** Изменять значения входящих параметров, в том числе полей переданных коллекций, запрещено без обоснованной необходимости (например, при передаче кэша). Если метод всё же изменяет параметр, это указывается в описании метода.
- **4.2.4** Для коллекций, которые возвращают экспортные методы области `ПрограммныйИнтерфейс`, создаются методы явного управления их полями: конструктор и методы чтения и установки значений. Вызывающий код не обращается к ключам структуры напрямую.

<details><summary>Примеры к 4.2</summary>

`Знач` при вызове сервера:

```bsl
// ❌ Плохо: таблица после вызова вернётся с сервера на клиент
&НаСервереБезКонтекста
Функция ЦеныРассчитать(Товары, ВидЦены)

// ✅ Хорошо
&НаСервереБезКонтекста
Функция ЦеныРассчитать(Знач Товары, Знач ВидЦены)
```

Изменение входящих параметров:

```bsl
// ❌ Плохо: функция возвращает сумму, но незаметно меняет переданную таблицу
Функция СуммаИтого(Товары)

	Результат = 0;
	Для Каждого ТоварыСтрока Из Товары Цикл
		ТоварыСтрока.Сумма = ТоварыСтрока.Цена * ТоварыСтрока.Количество;
		Результат = Результат + ТоварыСтрока.Сумма;
	КонецЦикла;

	Возврат Результат;

КонецФункции

// ✅ Хорошо: расчёт строк и подсчёт итога — два разных метода

// Рассчитывает суммы строк товаров.
Процедура СуммыРассчитать(Товары)

	Для Каждого ТоварыСтрока Из Товары Цикл
		ТоварыСтрока.Сумма = ТоварыСтрока.Цена * ТоварыСтрока.Количество;
	КонецЦикла;

КонецПроцедуры

// Итоговая сумма товаров.
Функция СуммаИтого(Товары)

	Результат = Товары.Итог("Сумма");

	Возврат Результат;

КонецФункции
```

Методы управления экспортной коллекцией (правило 4.2.4):

```bsl
// Общий модуль пр_ОтправкаПараметры

#Область ПрограммныйИнтерфейс

// Новые параметры отправки письма со значениями по умолчанию.
//
// Возвращаемое значение:
//	Структура - параметры отправки. Поля читаются и устанавливаются методами этого модуля.
//
Функция Создать() Экспорт

	Результат = Новый Структура;
	Результат.Вставить("Важность", ВажностьИнтернетПочтовогоСообщения.Обычная);
	Результат.Вставить("УведомлениеОПрочтении", Ложь);

	Возврат Результат;

КонецФункции

// Важность письма.
//
// Параметры:
//	Параметры - см. Создать
//
// Возвращаемое значение:
//	ВажностьИнтернетПочтовогоСообщения
//
Функция Важность(Параметры) Экспорт

	Результат = Параметры.Важность;

	Возврат Результат;

КонецФункции

// Устанавливает важность письма.
//
// Параметры:
//	Параметры - см. Создать
//	Значение - ВажностьИнтернетПочтовогоСообщения - новое значение.
//
Процедура ВажностьУстановить(Параметры, Значение) Экспорт

	Параметры.Важность = Значение;

КонецПроцедуры

#КонецОбласти
```

```bsl
// Использование
ОтправкаПараметры = пр_ОтправкаПараметры.Создать();
пр_ОтправкаПараметры.ВажностьУстановить(ОтправкаПараметры, ВажностьИнтернетПочтовогоСообщения.Высокая);
пр_Письмо.Отправить(Письмо, ОтправкаПараметры);
```

> Чтение и установка — разные методы: функция только возвращает значение, процедура только изменяет (см. CQRS в статье [Принципы программирования](../articles/principles.md#cqrs--разделение-чтения-и-изменения)). `ВажностьУстановить()` изменяет переданную структуру — это и есть её назначение, поэтому правило 4.2.3 не нарушено.

</details>

### 4.3 Функции

- **4.3.1** В функции ровно один оператор `Возврат`, и он стоит в конце. Исключение — функции с инструкциями препроцессора, если в итоговом (скомпилированном) коде всё равно остаётся один `Возврат`.
- **4.3.2** Результат функции хранится в переменной `Результат` (или в переменной с именем, совпадающим по смыслу с назначением функции).
- **4.3.3** Переменная результата инициализируется в начале функции значением по умолчанию.

<details><summary>Примеры к 4.3</summary>

```bsl
// ❌ Плохо: несколько выходов, в одной из веток результат не определён
Функция СкидкаПроцент(Клиент)

	Если НЕ ЗначениеЗаполнено(Клиент) Тогда
		Возврат 0;
	КонецЕсли;

	Если пр_Клиент.ПостоянныйЭто(Клиент) Тогда
		Процент = пр_Клиент.СкидкаПостоянная(Клиент);
	КонецЕсли;

	Возврат Процент;

КонецФункции

// ✅ Хорошо: результат инициализирован сразу, выход один

// Процент скидки клиента. Для непостоянных клиентов — 0.
Функция СкидкаПроцент(Клиент)

	Результат = 0;

	Если ЗначениеЗаполнено(Клиент)
		И пр_Клиент.ПостоянныйЭто(Клиент) Тогда

		Результат = пр_Клиент.СкидкаПостоянная(Клиент);

	КонецЕсли;

	Возврат Результат;

КонецФункции
```

</details>

### 4.4 Обработчики событий объектов

- **4.4.1** Обработчики событий записи проверяют `ОбменДанными.Загрузка` и собственные флаги отключения до выполнения действий и проверок. Сразу решите, какие действия нужны всегда, а какие — только при обычной записи (не при загрузке из обмена).
- **4.4.2** Предусматривается общий механизм отключения проверок `ПередЗаписью` через ключ дополнительного свойства.
- **4.4.3** Так же предусматривается общий механизм отключения действий, выполняемых в `ПриЗаписи` и `ОбработкаПроведения`.

<details><summary>Примеры к 4.4</summary>

```bsl
// Модуль объекта документа пр_ЗаявкаНаЗакупку

// BSLLS:MissingParameterDescription-off - см. синтакс-помощник
Процедура ПередЗаписью(Отказ, РежимЗаписи, РежимПроведения)

	Если ОбменДанными.Загрузка Тогда
		Возврат;
	КонецЕсли;

	Если НЕ пр_ОбъектПроверки.Отключены(ЭтотОбъект) Тогда
		СуммаЛимитПроверить(Отказ);
	КонецЕсли;

	ДокументСуммаРассчитать();

КонецПроцедуры
// BSLLS:MissingParameterDescription-on
```

```bsl
// Общий модуль пр_ОбъектПроверки

// Истина, если для записываемого объекта отключены проверки.
//
// Параметры:
//	Объект - ДокументОбъект, СправочникОбъект - записываемый объект.
//
// Возвращаемое значение:
//	Булево
//
Функция Отключены(Объект) Экспорт

	Результат = Объект.ДополнительныеСвойства.Свойство("пр_ПроверкиОтключены");

	Возврат Результат;

КонецФункции

// Отключает проверки при записи объекта.
//
// Параметры:
//	Объект - ДокументОбъект, СправочникОбъект - записываемый объект.
//
Процедура Отключить(Объект) Экспорт

	Объект.ДополнительныеСвойства.Вставить("пр_ПроверкиОтключены", Истина);

КонецПроцедуры
```

> Ранний `Возврат` из процедуры по `ОбменДанными.Загрузка` — обычный приём, так делают и типовые конфигурации. Правило одного `Возврат` (4.3.1) относится к функциям.

</details>

### 4.5 Прочее

- **4.5.1** Оператор `Перейти` не используется, кроме исключительных случаев.
- **4.5.2** По максимуму используются стандартные механизмы: платформенные, БСП и уже разработанные в проекте. Из БСП используется только программный интерфейс (область `ПрограммныйИнтерфейс`): служебный интерфейс может измениться в любом обновлении.
- **4.5.3** Доработанный функционал должен корректно работать под всеми ролями, которые предусматривает бизнес-логика. Тестируем под пользовательскими правами (с учётом RLS), а не только под полными.

## Пояснения и рекомендации

### Компактность

Небольшой метод можно охватить взглядом целиком, ему проще дать точное имя, его проще проверить. Размер метода не самоцель, но если метод не помещается на экран, почти всегда в нём можно выделить самостоятельные части.

**Операция слишком простая для отдельного метода?** Один из главных барьеров — нежелание создавать метод ради двух-трёх строк. Но такие методы:

- облегчают чтение: имя метода объясняет, что делают эти строки;
- сохраняют один уровень абстракции в вызывающем методе;
- спасают, когда простая операция со временем усложнится.

> ☝ Выделение фрагмента в метод с хорошим именем — один из лучших способов документировать код.

### Одна операция

**Метод выполняет одну операцию, выполняет её хорошо и больше ничего не делает.**

Как понять, что операция одна? Все действия метода находятся **на одном уровне абстракции**. Метод верхнего уровня описывает, *что* происходит, методы уровнем ниже — *как*:

```bsl
// ✅ Хорошо: верхний уровень читается как описание процесса

// Резервирует товары заказа и уведомляет менеджера.
//
// Параметры:
//	Заказ - ДокументСсылка.ЗаказКлиента - резервируемый заказ.
//
Процедура Выполнить(Заказ) Экспорт

	Товары = ТоварыОстатки(Заказ);
	ТоварыРезервировать(Заказ, Товары);
	МенеджерУведомить(Заказ);

КонецПроцедуры
```

Если в одном методе рядом стоят проверка прав, текст запроса, разбор его результата и формирование сообщения пользователю, — операций несколько, и метод нужно разделить.

### Спагетти-код

Спагетти-код — запутанный код, в котором перемешаны разнородные действия. Он может даже работать правильно и быстро, но его почти невозможно читать, отлаживать и менять: любая доработка превращается в «проще переписать».

**Признаки для самопроверки:**

- [ ] метод длиной в несколько экранов;
- [ ] вложенность больше трёх уровней, многоэтажные `Если … ИначеЕсли` с циклами внутри;
- [ ] переменные-флаги с ничего не говорящими именами (`Флаг2`, `Признак`);
- [ ] условия с двойным отрицанием и цепочками `И`/`ИЛИ` из пяти и более частей;
- [ ] перемешанные `Попытка` и транзакции, «проглоченные» исключения;
- [ ] метод решает несколько разных задач, которые делят общие переменные;
- [ ] комментарии, объясняющие, что делает очередной кусок кода.

Каждый признак по отдельности может быть оправдан. Несколько сразу — повод переписать.

### Хорошее имя метода

Имя метода — признак его качества. Если трудно подобрать короткое точное имя, скорее всего, метод делает слишком много или его назначение не продумано. Объектный стиль имён ([2.2](./02_names.md#22-объектный-стиль-имён)) помогает: он даёт однозначный критерий правильности имени и сразу подсказывает, в каком модуле должен лежать метод.

> ☝ Метод должен быть настолько простым, чтобы для документирования хватило удачного имени.

### Принцип наименьшего удивления

Метод делает то, чего от него ожидает читатель по имени. Никаких скрытых действий:

```bsl
// ❌ Плохо: по вызову непонятно, что прибавляется (дни? часы?)
// и не изменится ли переданная переменная
СрокОплаты = ДатуСдвинуть(ДатаДокумента, 5);

// ✅ Хорошо
СрокОплаты = пр_Дата.ДниРабочиеДобавить(ДатаДокумента, 5);
```

Имена вроде `ДанныеОбработать()` или `ВсеВыполнить()` ничего не сообщают. Если вам кажется, что код «хитрый», — для другого он окажется непонятным. **«Хитрый» код — это другое название плохого кода.** Всегда есть более простое решение.

### Нечитаемый код

Код, написанный самым неочевидным способом, который тем не менее как-то работает. Его ещё называют write-only: написать можно, прочитать — нет. Типичный пример — метод, поведение которого зависит не только от значений параметров, но и от их типов, а ошибки кодируются «магическими» значениями:

```bsl
// ❌ Плохо: проверка «это число?» превращена в загадку
Функция ЗначениеЧисло(Значение)

	Результат = -1;
	Попытка
		Результат = ?(Значение = Null, 0, Число(Значение));
	Исключение
		Результат = -1;
	КонецПопытки;

	Возврат Результат;

КонецФункции

// ✅ Хорошо: функция делает ровно то, что написано в имени

// Истина, если значение имеет тип «Число».
Функция ЧислоЭто(Значение)

	Результат = ТипЗнч(Значение) = Тип("Число");

	Возврат Результат;

КонецФункции
```

Почему `-1`? Почему `Null` превращается в ноль? Зачем `Попытка`? Каждый, кто будет сопровождать такой код, потратит время на эти вопросы.

### Небрежный код

Код, автор которого не знает базовых возможностей языка и не старается их узнать. Признаки: непродуманные имена, игнорирование стандартов, решения «лишь бы заработало», отсутствие форматирования. Такой код сложнее всего сопровождать, и именно он формирует плохую репутацию отрасли. Лекарство — стандарт, ревью и желание разобраться.

### Нелогичный код

Даже аккуратный разработчик иногда пишет код, который ставит читателя в тупик:

```bsl
// ❌ Плохо: взаимоисключающие ветки и сообщения, после которых непонятно, что делать
Если ОбработкаВыполнена И ОшибкиЕсть = Ложь Тогда
	ПоказатьПредупреждение(, "Обработка выполнена.");
ИначеЕсли ОбработкаВыполнена И ОшибкиЕсть = Истина Тогда
	ПоказатьПредупреждение(, "Обработка выполнена с ошибками!");
Иначе
	ПоказатьПредупреждение(, "При выполнении возникли ошибки!");
КонецЕсли;
```

Обработка одновременно «выполнена» и «с ошибками», а пользователь не узнаёт, какие ошибки и что с ними делать. Режимы работы, закодированные числами (`ВариантПечати = 0`), — из той же серии: `0` не ассоциируется с «предварительным просмотром». Используйте булев флаг (`ПечатьНаПринтер`) или перечисление.

### Мусор на входе — мусор на выходе

Если на вход алгоритма поданы некорректные данные, результат будет некорректным, даже если сам алгоритм верен ([GIGO](https://ru.wikipedia.org/wiki/GIGO)).

- За корректность входных данных отвечает **вызывающий** код. Чтобы его можно было правильно написать, у метода должно быть исчерпывающее описание параметров.
- Данные из внешних неконтролируемых источников (пользовательский ввод, файлы, внешние сервисы) проверяются на допустимые тип и состав в месте получения.

### Возвращаемое значение

Продумайте все пути выполнения функции и убедитесь, что значение возвращается на каждом. Инициализация результата в начале функции (правило 4.3.3) страхует от ситуации, когда в какой-то ветке результат не присвоен.

### Параметры

Чем больше параметров, тем сложнее вызывать и тестировать метод.

- Рекомендуется не более трёх основных параметров. Дополнительные передаются структурой четвёртым параметром. Для такой структуры создаётся конструктор (см. правило 4.2.4).
- Если параметров больше, скорее всего, они образуют отдельный объект, достойный собственного имени и модуля.
- Булев параметр-флаг обычно означает, что метод делает две разные вещи. Часто лучше сделать два метода с общим служебным третьим.
- Называйте параметры полно: `Ссылка` мало что говорит, `ЗаказСсылка` — говорит.

```bsl
// ❌ Плохо: девять параметров, из них пять булевых флагов
Функция ПисьмоСоздать(Пользователь, Данные = Неопределено, ВложенияПеренести = Ложь,
	Копирование = Ложь, ФорматHTML = Ложь, Дополнительно = Неопределено,
	Владелец = Неопределено, ПодписьДобавить = Ложь, Открыть = Истина) Экспорт

// ✅ Хорошо: основные параметры плюс структура дополнительных с конструктором
Функция ПисьмоСоздать(Пользователь, Основание, ПисьмоПараметры = Неопределено) Экспорт
```

### Вложенность

Чем глубже вложенность, тем сложнее читать код: приходится держать в голове все условия выше. **Вложенность не больше трёх уровней**, уже три — признак усложнённого кода. Как уменьшить:

- выделить тело цикла или ветки в отдельный метод;
- перенести сложное условие в функцию;
- переписать условия так, чтобы основной вариант обрабатывался первым.

### KISS: проще — лучше

> **Keep It Simple, Stupid** — «не усложняй».

Если задачу можно решить простым способом, её нужно решать простым способом. Принцип не просто рекомендует, а **запрещает** использовать более сложные инструменты, алгоритмы и структуры данных, чем требует задача.

Пример: нужно преобразовать число в строку длиной 6 символов с ведущими нулями.

```bsl
// ❌ Плохо: решение «в лоб» ветками
Если Номер < 10 Тогда
	НомерСтрока = "00000" + Формат(Номер, "ЧГ=0");
ИначеЕсли Номер < 100 Тогда
	НомерСтрока = "0000" + Формат(Номер, "ЧГ=0");
ИначеЕсли Номер < 1000 Тогда
	НомерСтрока = "000" + Формат(Номер, "ЧГ=0");
// ... и так далее
КонецЕсли;

// ❌ Лучше, но всё равно лишний код
НомерСтрока = Формат(Номер, "ЧГ=0");
Пока СтрДлина(НомерСтрока) < 6 Цикл
	НомерСтрока = "0" + НомерСтрока;
КонецЦикла;

// ✅ Хорошо: возможность платформы
НомерСтрока = Формат(Номер, "ЧЦ=6; ЧВН=; ЧГ=0");
```

Первый вариант — типичный копипаст: если что-то можно скопировать и вставить, оно будет скопировано. Такой код разрастается, и при любом изменении его приходится править в нескольких местах.

### Оверинжиниринг

Обратная крайность — решать простую задачу самым сложным и «технологичным» способом: многоуровневые механизмы, универсальные схемы, абстракции «на будущее».

Проблема не в качестве такого кода, а в стоимости его сопровождения. Типичная ситуация: нужно поменять одну надпись в одной печатной форме. Выясняется, что все формы строятся одним универсальным механизмом через несколько уровней временных таблиц и общий макет. Поиск места занимает часы, а правка меняет надпись сразу во всех формах. Отделить нужную форму нельзя без переписывания половины механизма.

> ⚠️ Оверинжиниринг уничтожает главное преимущество платформы 1С — открытость кода и возможность быстро дорабатывать его силами специалистов средней квалификации.

### Используйте готовое

Никто, строя дом, не делает сам холодильник и окна, если их можно купить. Прежде чем писать сложный метод, проверьте, нет ли готовой реализации в платформе, БСП или проекте.

Обратная ошибка — сознательный отказ от библиотечных функций и даже методов платформы «потому что не доверяю» и написание всего вручную. Такой код тоже работает, но разработка обходится дороже, а ручные реализации ещё и копируются по конфигурации.

### YAGNI: только то, что нужно

> **You Aren't Gonna Need It** — «вам это не понадобится».

Реализуется только то, что решает реальную задачу. Функции «на всякий случай» стоят денег при разработке и при сопровождении, а нужны редко. Заказчику нужны не формы и кнопки, а решённая задача. Часто он описывает не задачу, а способ решения, — задача разработчика выяснить, что на самом деле нужно.

### Связанное — рядом

Код должен читаться сверху вниз, без прыжков. Объявляйте переменную рядом с местом первого использования: если определение и использование разделяет сотня строк, читатель теряет место чтения, пока ищет определение. Исключение — переменная результата функции (правило 4.3.3).

### Не уверен — не трогай

> ⚠️ Если в системе что-то кажется странным, ошибочным или лишним, но нет понимания, зачем оно такое и что будет после исправления, — не трогайте.

На понимание алгоритма нужно потратить столько времени, сколько требуется. Сэкономить его не получится: быстрая правка без понимания почти наверняка потребует исправления собственных ошибок, и разбираться всё равно придётся.

Пример. Разработчик, принявший систему на сопровождение, решил навести порядок и отсортировал все объекты метаданных по алфавиту, включая значения перечислений. После обновления расчёты начали выдавать неверные результаты. Оказалось, в системе было перечисление с названиями месяцев, а одна функция определяла номер месяца по порядковому номеру значения перечисления. Сортировка превратила январь в август.

**Без полного понимания механизма его не меняют.**
