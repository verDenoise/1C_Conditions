# 2. Имена

[Оглавление](./README.md) | Назад: [1. Введение](./01_intro.md) | Далее: [3. Модули и области](./03_modules.md)

## Правила

### 2.1 Общие правила

- **2.1.1** Имя осмысленно и однозначно отражает назначение. Исключение — тривиальные переменные вроде счётчика короткого цикла. При необходимости в конце имени указывается вид содержимого: `КонтрагентСсылка`, `КонтрагентОбъект`, `ДокументыМассив`, `ЗаписиНабор`.
- **2.1.2** В именах нет орфографических ошибок.
- **2.1.3** Произвольные сокращения запрещены (`ОприхТовНаГлСкл`). Слова пишутся полностью. Допускаются общепринятые аббревиатуры: `НДС`, `ИНН`, `ЦФО`, `SQL`.
- **2.1.4** В именах запрещена частица `Не`. Булевы имена — утвердительные (см. 2.4.3).
- **2.1.5** Имя начинается с заглавной буквы, каждое следующее слово — тоже ([CamelCase](https://ru.wikipedia.org/wiki/CamelCase)). Исключение — имена ресурсов, доступных извне: для них используется принятый у ресурса стиль (например, для URL HTTP-сервисов — нижний регистр, [snake_case](https://ru.wikipedia.org/wiki/Snake_case)).
- **2.1.6** Имена только русские. Исключения:
  - код, работающий с внешними компонентами;
  - работа с внешними приложениями и объектами (COM, OLE);
  - web- и HTTP-сервисы;
  - системные имена, которые задаёт платформа.
- **2.1.7** Одинаковые по смыслу сущности называются одинаково во всём проекте, разные — по-разному. Перед созданием нового модуля согласуйте имена с командой: нужные сущности могли уже появиться у коллег.
- **2.1.8** Имена нетиповых объектов конфигурации, общих модулей, глобальных переменных и методов, а также ключей, добавляемых в `ДополнительныеСвойства` объектов, начинаются с **префикса подсистемы и знака подчёркивания**: `пр_ЗаказКлиента`, `пр_ПроверкиОтключены`. Если выделенной подсистемы нет, используется префикс проекта. В остальных случаях знак подчёркивания в именах запрещён.
- **2.1.9** Имена объектов метаданных — справочников, документов, регистров, отчётов, обработок, подписок, регламентных заданий и т. д. — строятся по [правилам 1С](https://its.1c.ru/db/v8std/content/550/hdoc) естественным русским языком. Объектный стиль (2.2) к ним не применяется. Исключение — общие модули (см. 2.2.2–2.2.5). Подробнее — в [10. Объекты метаданных](./10_metadata.md).

<details><summary>Примеры к 2.1</summary>

```bsl
// ❌ Плохо
ОприхТовНаГлСкл = Истина;          // сокращения
ДокНеПроведен = Ложь;              // сокращение и частица «Не»
Массив = НайтиДокументы(Партнер);  // имя не говорит, что внутри
ОтключитьПроверки = Истина;        // ключ ДополнительныеСвойства без префикса может совпасть с типовым

// ✅ Хорошо
ТоварыОприходованы = Истина;
ДокументПроведен = Истина;
ЗаказыМассив = ПартнерЗаказы(Партнер);
ДокументОбъект.ДополнительныеСвойства.Вставить("пр_ПроверкиОтключены", Истина);
```

</details>

### 2.2 Объектный стиль имён

- **2.2.1** Имена элементов кода — переменных, параметров, методов и общих модулей — строятся в **объектном стиле**: сначала объект, затем его свойство, затем свойство свойства, а в самом конце — действие или признак.

  > `Объект[.Свойство[.Свойство]][.Метод()]`
  >
  > Большее содержит меньшее и стоит слева. Действие (глагол) или признак относится к последнему элементу и стоит справа.

- **2.2.2** Общий модуль рассматривается как объект (класс со статическими методами). Имя модуля — это «объектная» часть полного имени, имя метода — оставшаяся часть. Точки в полном имени убираются, первый объект обычно уходит в префикс подсистемы.
- **2.2.3** Имя метода не повторяет имя своего модуля: `пр_Документ.НакладнаяЭто()`, а не `пр_Документ.ДокументНакладнаяЭто()`.
- **2.2.4** Имя общего модуля — существительное (или цепочка существительных) в именительном падеже, обозначающее объект, которым управляют методы модуля. В 95% случаев — в единственном числе: не `УправлениеДиалогом`, а `Диалог`. Модуль во множественном числе (`Отчеты`) управляет набором объектов, а не одним объектом.
- **2.2.5** Суффикс общего модуля обозначает контекст выполнения и задаётся по [стандарту 1С](https://its.1c.ru/db/v8std/content/469/hdoc). Основные случаи:

  | Модуль | Суффикс | Пример |
  |---|---|---|
  | Серверный | без суффикса | `прс_ЗагрузкаФайл` |
  | Серверный, вызываемый с клиента | `ВызовСервера` | `прс_ЗагрузкаФайлВызовСервера` |
  | Клиентский | `Клиент` | `прс_ЗагрузкаФайлКлиент` |
  | Клиент-серверный | `КлиентСервер` | `прс_ЗагрузкаФайлКлиентСервер` |
  | Серверный привилегированный | `Привилегированный` | `прс_ЗагрузкаФайлПривилегированный` |
  | С повторным использованием значений | `ПовтИсп` (`КлиентПовтИсп`) | `прс_ЗагрузкаНастройкаПовтИсп` |
  | Глобальный | `Глобальный` | `прс_ЗагрузкаГлобальный` |

  Суффикс стоит после объектной части имени и в объектный порядок слов не входит.

> Объектный стиль не противоречит стандартам 1С: они не задают порядок слов в именах переменных, методов и общих модулей. Зачем он нужен и чем отличается от «разговорного» стиля типовых конфигураций, разобрано в статье [Объектный стиль имён](../articles/object_style.md).

<details><summary>Примеры к 2.2</summary>

Полное имя «по-объектному» и то, как оно раскладывается на модуль и метод:

| Полное имя | Модуль | Метод |
|---|---|---|
| `ЗаказКлиента.Согласование.Задача.Обновить()` | `зкк_СогласованиеЗадача` | `Обновить()` |
| `Логистика.Контейнер.Маршрут.Точка.Текущая()` | `лгс_КонтейнерМаршрут` | `ТочкаТекущая()` |
| `Прайс.Загрузка.Файл.Прочитать()` | `прс_ЗагрузкаФайл` | `Прочитать()` |
| `Прайс.Загрузка.Настройка.Сохранить()` | `прс_ЗагрузкаНастройка` | `Сохранить()` |

```bsl
// ❌ Плохо: «разговорные» имена, модуль-свалка, имя метода повторяет модуль
ПрайсЗагрузкаСервер.ЗагрузитьПрайсИзФайла(ИмяФайла);
ПрайсЗагрузкаСервер.ПолучитьНастройкиЗагрузкиПрайса();
ПрайсЗагрузкаСервер.ПроверитьКорректностьФайлаПрайса(ИмяФайла);

// ✅ Хорошо: у каждого объекта свой модуль, метод — действие над ним
прс_ЗагрузкаФайл.Загрузить(ИмяФайла);
прс_ЗагрузкаНастройка.Прочитать();
прс_ЗагрузкаФайл.Корректен(ИмяФайла);
```

</details>

### 2.3 Имена методов

- **2.3.1** Процедура называется по схеме «объект + действие». Действие — глагол в неопределённой форме совершенного вида, отвечающий на вопрос «что сделать?», и стоит в конце: `ПисьмоОтправить()`, `ТоварыЗаполнить()`, `СтатусУстановить()`.
- **2.3.2** Функция называется тем, что она возвращает. Глагол `Получить` не пишется: `ЦенаРозничная()`, а не `ПолучитьРозничнуюЦену()`. Функция не изменяет состояние системы. Исключение — функции, создающие и возвращающие новый объект или коллекцию: действие указывается в конце имени — `Создать()`, `ЗаказСоздать()`.
- **2.3.3** Функция, возвращающая булево значение, называется так, как звучит её истинный результат. Если в конце имени поставить знак вопроса, должна получиться осмысленная фраза: `СтрокиДублиЕсть()`, `НакладнаяЭто()`, `ЗначениеДоступно()`, `СхемаКорректна()`.
- **2.3.4** Функция-преобразователь называется по схеме `<Исходное>В<Результат>`: `СтрокаВЧисло()`, `ОтборВТаблица()`, `КонтрагентыВДоговорыОсновные()`.
- **2.3.5** Серверные методы модуля формы, выполняемые с контекстом, заканчиваются на `НаСервере`: `ТоварыЗаполнитьНаСервере()`.

<details><summary>Примеры к 2.3</summary>

```bsl
// ❌ Плохо
Процедура ОтправкаПисьма(Письмо)                 // существительное вместо действия
Функция ПолучитьЦенуНоменклатуры(Номенклатура)   // лишнее «Получить», «разговорный» порядок слов
Функция ПроверитьДубли(Товары)                   // по имени непонятно, что значит Истина
Функция НеЗаполненаОрганизация(Документ)         // отрицание в имени

// ✅ Хорошо
Процедура ПисьмоОтправить(Письмо)
Функция НоменклатураЦена(Номенклатура)
Функция ТоварыДублиЕсть(Товары)
Функция ОрганизацияЗаполнена(Документ)
```

</details>

### 2.4 Имена переменных

- **2.4.1** Переменная называется в том же объектном стиле: `КонтрагентыТаблица`, `РегионНаименование`, `ОстатокКоличество`.
- **2.4.2** Имя отражает содержимое, а не тип, если тип и так очевиден. Если в имени указан тип, он должен совпадать с действительным: переменная `ДокументыМассив` содержит массив.
- **2.4.3** Булева переменная называется так, как звучит её истинное значение: `ДокументПроведен`, `ОстаткиКонтролируются`.
- Остальные правила для переменных — в [5. Переменные](./05_variables.md).

## Пояснения и рекомендации

### Имя полностью описывает сущность

Хороший способ придумать имя — сформулировать словами, что хранит переменная или делает метод. Эта формулировка, упорядоченная по объектному стилю, чаще всего и есть лучшее имя. Оно однозначно, не требует расшифровки и легко запоминается.

**Если имени нужен комментарий, значит, имя выбрано неудачно.**

Не бойтесь переименовывать. Если придумали имя лучше — замените. Конфигуратор и EDT умеют переименовывать переменную во всём методе.

### Имена не должны вводить в заблуждение

- Не указывайте в имени тип, которого там нет: `СсылкиМассив`, в котором на самом деле лежит таблица значений, хуже, чем просто `Ссылки`.
- Не используйте похожие имена для разных сущностей и разные имена для одной сущности. Если в одном модуле есть `ИнформацияТовар`, `СведенияТовар` и `ДанныеТовар`, читатель будет искать между ними разницу, которой нет.
- Избегайте имён, отличающихся одним словом в середине. Автодополнение показывает их рядом, и ошибиться легко:

```bsl
// ❌ Плохо: имена почти не отличаются
Для Каждого СтрокаСкидкиКартыПокупателя Из СтрокиСкидкиКартыПокупателя Цикл
	СтрокаСкидкиКартыПокупателя.Процент = ПроцентСкидки;
КонецЦикла;

// ✅ Хорошо: коллекция и её элемент явно различаются
Для Каждого КартаСтрока Из КартыСкидкиТаблица Цикл
	КартаСтрока.Процент = СкидкаПроцент;
КонецЦикла;
```

### Имена без смысла

Числовые ряды `Структура1`, `Структура2`, `Массив3` и слова-пустышки (`Данные`, `Информация`, `Значение`, `Врем`) ничего не сообщают о назначении. Если из имени можно убрать слово и смысл не изменится, это слово лишнее: `НаименованиеСтрокой` ничем не лучше `Наименование`.

### Длина имени

Длина имени соответствует его области видимости и значимости:

- счётчик короткого цикла в пять строк может называться коротко;
- переменная, которая используется в разных частях метода, называется полно;
- экспортный метод или переменная модуля — самые подробные имена.

Слишком длинные имена тоже мешают: их трудно прочитать с ходу, и они размывают структуру кода. Однобуквенные имена трудно искать поиском, и они «временные» только в теории.

### Сокращения и аббревиатуры

Мозг всё равно пытается расшифровать сокращение, поэтому оно не экономит время чтения, а тратит его. Кроме того, сокращения каждый произносит по-своему, и обсуждать такой код неудобно. Общеизвестные аббревиатуры (`НДС`, `РФ`, `ИНН`) допустимы: они короче и понятны всем. Малоизвестные — расшифровываем.

### Префиксы

Префиксы типа `м_`, `тз_`, `стр` не нужны: читатель всё равно их отбрасывает, а смысл префикса приходится угадывать (`м_Цены` — массив? модуль? моя переменная?). Знак подчёркивания в начале имени (`_Структура`) — тот же префикс, только ещё менее понятный.

Единственный обязательный префикс — **префикс подсистемы** (правило 2.1.8). Он нужен, чтобы:

- имена наших объектов не пересекались с типовыми, в том числе в расширениях;
- по имени было видно, к какой подсистеме относится объект.

### Никаких шуток и игры слов

Имя понятно только тому, кто знает контекст шутки. Одно слово в двух разных смыслах — такой же каламбур. Выбирайте ясность, а не остроумие.

### Лишний контекст

Не добавляйте в имя больше контекста, чем нужно. Внутри модуля `пр_ЗаказКлиента` метод не нужно называть `ЗаказКлиентаТоварыЗаполнить()` — достаточно `ТоварыЗаполнить()`. Проверка простая: уберите часть имени; если смысл не изменился, эта часть лишняя.
