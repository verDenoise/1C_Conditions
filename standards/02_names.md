# 2. Имена

[↑ Оглавление](./README.md)

> Как называть переменные, методы и модули так, чтобы имя объясняло код без комментариев.

**Коротко**

- Имя полностью и точно описывает то, что за ним стоит. Сокращений нет.
- Код именуем в **объектном стиле**: сначала объект, в конце — действие или признак (`ПисьмоОтправить`, `ТоварыДублиЕсть`).
- Объекты метаданных, кроме общих модулей, называем по правилам 1С.
- Нетиповые объекты и ключи `ДополнительныеСвойства` начинаются с префикса подсистемы: `пр_`.

## Правила

### 2.1 Общие правила

- **2.1.1** Имя осмысленно и однозначно отражает назначение. Исключение — счётчик короткого цикла. Если нужно, в конце имени указывается вид содержимого: `КонтрагентСсылка`, `КонтрагентОбъект`, `ДокументыМассив`, `ЗаписиНабор`.
- **2.1.2** В именах нет орфографических ошибок.
- **2.1.3** Произвольные сокращения запрещены, слова пишутся полностью. Допускаются только общеизвестные аббревиатуры: `НДС`, `ИНН`, `ЦФО`, `SQL`.
- **2.1.4** Частица `Не` в именах запрещена. Булевы имена — только утвердительные (2.4.3).
- **2.1.5** Каждое слово в имени начинается с заглавной буквы ([CamelCase](https://ru.wikipedia.org/wiki/CamelCase)). Исключение — имена, видимые снаружи: для них действует стиль внешней системы. Например, адреса HTTP-сервисов пишутся строчными буквами через подчёркивание ([snake_case](https://ru.wikipedia.org/wiki/Snake_case)).
- **2.1.6** Имена — на русском языке. Латиница допустима только там, где её требует внешний мир:
  - внешние компоненты, COM- и OLE-объекты;
  - web- и HTTP-сервисы, форматы обмена (JSON, XML);
  - системные имена, которые задаёт платформа.
- **2.1.7** Одинаковые по смыслу сущности называются одинаково во всём проекте, разные — по-разному. Прежде чем вводить новое имя, проверьте, не появилось ли оно уже у коллег.
- **2.1.8** Имена нетиповых объектов конфигурации, общих модулей, глобальных переменных и методов, а также ключей `ДополнительныеСвойства` начинаются с **префикса подсистемы и подчёркивания**: `пр_ЗаказКлиента`, `пр_ПроверкиОтключены`. Если выделенной подсистемы нет, используется префикс проекта. В остальных случаях подчёркивание в именах запрещено.
- **2.1.9** Объекты метаданных — справочники, документы, регистры, отчёты, обработки, подписки, регламентные задания и т. д. — называются по [правилам 1С](https://its.1c.ru/db/v8std/content/550/hdoc), естественным русским языком. Объектный стиль (2.2) к ним не применяется. Исключение — общие модули. Подробнее — в главе [10. Объекты метаданных](./10_metadata.md).

<details><summary>Примеры к 2.1</summary>

```bsl
// ❌ Плохо
ОприхТовНаГлСкл = Истина;          // сокращения
ДокНеПроведен = Ложь;              // сокращение и частица «Не»
Массив = НайтиДокументы(Партнер);  // имя не говорит, что внутри
ОтключитьПроверки = Истина;        // ключ ДополнительныеСвойства без префикса может совпасть с типовым

// ✅ Хорошо
ТоварыОприходованы = Истина;
ДокументПроведен = Истина;
ЗаказыМассив = ПартнерЗаказы(Партнер);
ДокументОбъект.ДополнительныеСвойства.Вставить("пр_ПроверкиОтключены", Истина);
```

Имена, видимые снаружи (2.1.5, 2.1.6):

```bsl
// Шаблон URL HTTP-сервиса: /orders/{order_id}/status
// Поля JSON — так, как их ждёт внешняя система
ОтветДанные = Новый Структура;
ОтветДанные.Вставить("order_id", ЗаказНомер);
ОтветДанные.Вставить("status", СтатусКод);
```

</details>

### 2.2 Объектный стиль

- **2.2.1** Имена элементов кода — переменных, параметров, методов, общих модулей — строятся в **объектном стиле**: сначала объект, затем его свойства, в самом конце — действие или признак.

  > `Объект[.Свойство[.Свойство]][.Метод()]`
  >
  > Большее содержит меньшее и стоит левее. Действие или признак относится к последнему элементу и стоит правее всех.

- **2.2.2** Общий модуль — это объект, а его экспортные методы — действия над этим объектом. Полное имя раскладывается так: первый объект уходит в префикс подсистемы, промежуточные — в имя модуля, последнее действие — в имя метода.
- **2.2.3** Имя метода не повторяет имя модуля: `пр_Документ.НакладнаяЭто()`, а не `пр_Документ.ДокументНакладнаяЭто()`.
- **2.2.4** Имя общего модуля — существительное (или цепочка существительных) в именительном падеже: тот объект, которым управляют методы модуля. Почти всегда — в единственном числе: не `УправлениеДиалогом`, а `Диалог`. Множественное число (`Отчеты`) означает, что модуль управляет набором объектов, а не одним.
- **2.2.5** Суффикс общего модуля обозначает контекст выполнения и ставится по [стандарту 1С](https://its.1c.ru/db/v8std/content/469/hdoc). Он идёт после объектной части имени и в объектный порядок слов не входит.

  | Модуль | Суффикс | Пример |
  |---|---|---|
  | Серверный | — | `прс_ЗагрузкаФайл` |
  | Серверный, вызываемый с клиента | `ВызовСервера` | `прс_ЗагрузкаФайлВызовСервера` |
  | Клиентский | `Клиент` | `прс_ЗагрузкаФайлКлиент` |
  | Клиент-серверный | `КлиентСервер` | `прс_ЗагрузкаФайлКлиентСервер` |
  | Привилегированный | `ПолныеПрава` | `прс_ЗагрузкаФайлПолныеПрава` |
  | С повторным использованием значений | `ПовтИсп`, `КлиентПовтИсп` | `прс_ЗагрузкаНастройкаПовтИсп` |
  | Глобальный | `Глобальный` | `прс_ЗагрузкаГлобальный` |

> Объектный стиль не противоречит стандартам 1С: они не задают порядок слов в именах переменных, методов и общих модулей. Зачем он нужен и чем отличается от привычного «разговорного» стиля, разобрано в статье [Объектный стиль имён](../articles/object_style.md).

<details><summary>Примеры к 2.2</summary>

Как полное имя раскладывается на модуль и метод:

| Полное имя | Модуль | Метод |
|---|---|---|
| `ЗаказКлиента.Согласование.Задача.Обновить()` | `зкк_СогласованиеЗадача` | `Обновить()` |
| `Логистика.Контейнер.Маршрут.Точка.Текущая()` | `лгс_КонтейнерМаршрут` | `ТочкаТекущая()` |
| `Прайс.Загрузка.Файл.Прочитать()` | `прс_ЗагрузкаФайл` | `Прочитать()` |
| `Прайс.Загрузка.Настройка.Сохранить()` | `прс_ЗагрузкаНастройка` | `Сохранить()` |

```bsl
// ❌ Плохо: «разговорные» имена, всё в одном модуле, имя метода повторяет модуль
ПрайсЗагрузкаСервер.ЗагрузитьПрайсИзФайла(ИмяФайла);
ПрайсЗагрузкаСервер.ПолучитьНастройкиЗагрузкиПрайса();
ПрайсЗагрузкаСервер.ПроверитьКорректностьФайлаПрайса(ИмяФайла);

// ✅ Хорошо: у каждого объекта свой модуль, метод — действие над ним
прс_ЗагрузкаФайл.Загрузить(ИмяФайла);
прс_ЗагрузкаНастройка.Прочитать();
прс_ЗагрузкаФайл.Корректен(ИмяФайла);
```

</details>

### 2.3 Имена методов

- **2.3.1** Процедура называется по схеме «объект + действие». Действие — глагол совершенного вида в неопределённой форме («что сделать?») и стоит в конце: `ПисьмоОтправить()`, `ТоварыЗаполнить()`, `СтатусУстановить()`.
- **2.3.2** Функция называется тем, что возвращает. Глагол `Получить` не пишется: `ЦенаРозничная()`, а не `ПолучитьРозничнуюЦену()`. Функция не меняет состояние системы. Исключение — функции, которые создают и возвращают новый объект или коллекцию: действие пишется в конце имени — `Создать()`, `ЗаказСоздать()`.
- **2.3.3** Булева функция называется так, как звучит её истинный результат. Если в конце имени поставить знак вопроса, должна получиться осмысленная фраза: `СтрокиДублиЕсть()`, `НакладнаяЭто()`, `ЗначениеДоступно()`, `СхемаКорректна()`.
- **2.3.4** Функция-преобразователь называется по схеме `<Исходное>В<Результат>`: `СтрокаВЧисло()`, `ОтборВТаблица()`, `КонтрагентыВДоговорыОсновные()`.
- **2.3.5** Серверный метод модуля формы, выполняемый с контекстом, заканчивается на `НаСервере`: `ТоварыЗаполнитьНаСервере()`.
- **2.3.6** Имя метода не совпадает с зарезервированным словом языка — `Выполнить`, `Новый`, `Перейти`, `Возврат` и т. п.: такой метод не скомпилируется. Вместо `Выполнить()` называем конкретное действие: `Провести()`, `Запустить()`, `Резервировать()`.

<details><summary>Примеры к 2.3</summary>

```bsl
// ❌ Плохо
Процедура ОтправкаПисьма(Письмо)                 // существительное вместо действия
Функция ПолучитьЦенуНоменклатуры(Номенклатура)   // лишнее «Получить», «разговорный» порядок слов
Функция ПроверитьДубли(Товары)                   // непонятно, что означает Истина
Функция НеЗаполненаОрганизация(Документ)         // отрицание в имени
Функция ПреобразоватьДатуВСтроку(Дата)           // глагол лишний

// ✅ Хорошо
Процедура ПисьмоОтправить(Письмо)
Функция НоменклатураЦена(Номенклатура)
Функция ТоварыДублиЕсть(Товары)
Функция ОрганизацияЗаполнена(Документ)
Функция ДатаВСтрока(Дата)
```

Так имена читаются в месте вызова:

```bsl
Если пр_Заказ.ТоварыДублиЕсть(Заказ.Товары) Тогда       // «у заказа есть дубли товаров?»
	пр_ЗаказТовары.ДублиСвернуть(Заказ.Товары);
КонецЕсли;
```

</details>

### 2.4 Имена переменных

- **2.4.1** Переменная называется в том же объектном стиле: `КонтрагентыТаблица`, `РегионНаименование`, `ОстатокКоличество`.
- **2.4.2** Имя отражает содержимое. Тип указывается, только если он помогает понять код. Указанный в имени тип совпадает с действительным: в `ДокументыМассив` лежит массив.
- **2.4.3** Булева переменная называется так, как звучит её истинное значение: `ДокументПроведен`, `ОстаткиКонтролируются`.
- Остальные правила — в главе [5. Переменные](./05_variables.md).

<details><summary>Примеры к 2.4</summary>

```bsl
// ❌ Плохо
ТаблицаКонтрагентов = Запрос.Выполнить().Выгрузить(); // «разговорный» порядок слов
СсылкиМассив = Запрос.Выполнить().Выгрузить();        // в имени массив, а на деле таблица
Флаг = Документ.Проведен;                              // непонятно, что значит Истина

// ✅ Хорошо
КонтрагентыТаблица = Запрос.Выполнить().Выгрузить();
ДокументПроведен = Документ.Проведен;
```

</details>

## Пояснения

### Хорошее имя — это описание

Самый надёжный способ придумать имя — сказать словами, что хранит переменная или делает метод, и упорядочить эту фразу по объектному стилю. Такое имя однозначно, не требует расшифровки и легко запоминается.

**Если имени нужен комментарий, имя выбрано неудачно.**

Не бойтесь переименовывать: придумали лучше — замените. Конфигуратор и EDT умеют переименовывать переменную во всём методе.

### Имя не должно вводить в заблуждение

- Не указывайте в имени тип, которого там нет: `СсылкиМассив`, в котором лежит таблица значений, хуже, чем просто `Ссылки`.
- Не называйте одно разными словами. Если в модуле живут `ИнформацияТовар`, `СведенияТовар` и `ДанныеТовар`, читатель будет искать между ними разницу, которой нет.
- Избегайте имён, которые различаются одним словом в середине: автодополнение показывает их рядом, и ошибиться легко.

```bsl
// ❌ Плохо: коллекцию и её элемент легко перепутать
Для Каждого СтрокаСкидкиКартыПокупателя Из СтрокиСкидкиКартыПокупателя Цикл
	СтрокаСкидкиКартыПокупателя.Процент = ПроцентСкидки;
КонецЦикла;

// ✅ Хорошо
Для Каждого КартаСтрока Из КартыСкидкиТаблица Цикл
	КартаСтрока.Процент = СкидкаПроцент;
КонецЦикла;
```

### Пустые имена

Числовые ряды (`Структура1`, `Структура2`) и слова-пустышки (`Данные`, `Информация`, `Значение`, `Врем`) ничего не говорят о назначении. Проверка простая: если слово можно убрать без потери смысла, оно лишнее. `НаименованиеСтрокой` ничем не лучше `Наименование`.

### Длина имени

Длина имени соответствует области видимости:

- счётчик цикла на пять строк может называться коротко;
- переменная, которая используется по всему методу, называется полно;
- у экспортного метода и переменной модуля — самые подробные имена.

Слишком длинные имена тоже мешают: их трудно охватить взглядом, и они размывают структуру кода. Однобуквенные плохо находятся поиском и остаются «временными» только в теории.

### Сокращения

Мозг всё равно расшифровывает сокращение, поэтому оно не экономит время чтения, а тратит его. К тому же сокращения каждый произносит по-своему, и обсуждать такой код неудобно. Общеизвестные аббревиатуры (`НДС`, `ИНН`, `РФ`) — исключение: они короче и понятны всем.

### Префиксы

Префиксы вида `м_`, `тз_`, `стр` не нужны: читатель их всё равно отбрасывает, а смысл приходится угадывать (`м_Цены` — массив? модуль? «моя» переменная?). Подчёркивание в начале имени (`_Структура`) — тот же префикс, только ещё менее понятный.

Обязателен только **префикс подсистемы** (2.1.8). Он нужен, чтобы:

- наши имена не пересекались с типовыми, в том числе в расширениях;
- по имени было видно, к какой подсистеме относится объект.

### Без шуток

Шутку в имени понимает только тот, кто знает её контекст. Одно слово в двух разных смыслах — такой же каламбур. Выбирайте ясность, а не остроумие.

### Лишний контекст

Не добавляйте в имя то, что и так ясно из окружения. Внутри модуля `пр_ЗаказКлиента` метод не нужно называть `ЗаказКлиентаТоварыЗаполнить()` — достаточно `ТоварыЗаполнить()`.
