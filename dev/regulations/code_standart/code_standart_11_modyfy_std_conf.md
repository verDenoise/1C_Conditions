# <img src="./images/11_modified.png" align=top height=25 width=25/> 11. Модификация типового функционала

* **11.1** Стараемся минимизировать изменение типовых объектов. Любое изменение типового объекта конфигурации должно иметь аргументированное обоснование.
* **11.2** Изменения типового кода и/или типовых реквизитов допускаются в исключительных случаях и **в обязательном порядке** должны иметь отметку в документации проекта.
* **11.3** Проектные расширения должны являться отдельными подсистемами в рамках БСП. Обновление и описаний версий проектных расширений выполняем с использованием [библиотеки обновления компонент](https://gitlab.com/bsl-libs/update_components_ext) или [стандартного функционала обновлений БСП](https://its.1c.ru/db/v8std/content/690/hdoc)
* **11.4** Расширения, изменяющие типовой функционал должны в явном виде содержать перечень вносимых изменений и/или иметь внешнюю документацию с описанием вносимых изменений.
* **11.5** Новые объекты хранимых данных (новые хранимые объекты/реквизиты) вносим в конфигурацию.
* **11.6** Для минимизации корректировки типовых объектов следует использовать расширения, при этом в общем случае используем в расширении:
  - Для изменения процедур, вызываемых по событиям - подписки на события
  - Для изменения форм - программную модификацию форм
  - Для прочих изменяемых методов - используем инструкции препроцессора &Перед и &После, использование инструкции &Вместо допустимо только при наличии вызова `ПродолжитьВызов()`. &КонтрольИИзменение используем при отсутствии других вариантов модификации
* **11.7** При изменении кода типовой конфигурации необходимо обрамлять код комментариями с использованием следующих шаблонов
  - Добавленный в типовые объекты код
    > ```bsl
    > // [+] #<Номер задачи> <ИмяПользователяХранилища> <ТекущаяДата> {
    > Добавленный код
    > // } #<Номер задачи> <ИмяПользователяХранилища> <ТекущаяДата>
    > ```
  - Измененный в типовых объектах код, необходимо сохранить типовой код в закомментированном виде
    > ```bsl
    > // [*] #<Номер задачи> <ИмяПользователяХранилища> <ТекущаяДата> {
    > // Закомментиированный типовой код
    > Добавленный код
    > // } #<Номер задачи> <ИмяПользователяХранилища> <ТекущаяДата>
    > ```
  - Удаленный типовой код , необходимо сохранить типовой код в закомментированном виде
    > ```bsl
    > // -] #<Номер задачи> <ИмяПользователяХранилища> <ТекущаяДата> {
    > // Закомментиированный типовой код
    > // } #<Номер задачи> <ИмяПользователяХранилища> <ТекущаяДата>
    > ```
* **11.8** Новые методы необходимо размещать в нетиповых общих модулях, размещенных в расширении доработок. Запрещено добавлять методы в типовые общие модули.
* **11.9** При внесении изменений в типовой код нельзя переформатировать модули целиком (изменять отступы), не нужно вставлять пустых строк. Сравнение конфигураций должно показать только реальные изменения.
* **11.10** При модификации типовой конфигурации необходимо понимать, что "минимальное изменение типовых объектов и кода" не есть основной критерий, который определит трудоемкость последующих обновлений. С одной стороны, нужно добиться минимизации ручного переноса изменений в новые релизы, но с другой стороны требуется обеспечить надежный перенос всех изменений в следующий релиз (обеспечение простоты анализа изменений при помощи механизмов сравнения и объединения) и адаптацию к новому релизу (если есть такая необходимость). Поэтому практика копирования многострочных (например, более 20 строк) запросов и изменения в них пары строчек, копирования типовых форм ради добавления пары элементов формы на них и т.п. признана вредной. Вместо копирования объектов следует использовать точечно вносимые программные изменения.
