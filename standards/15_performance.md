# 15. Производительность

[↑ Оглавление](./README.md)

> Когда и как оптимизировать код, и где обычно теряется время.

**Коротко**

- Сначала понятность, потом скорость. Усложняющая оптимизация — только по результатам замеров.
- Если быстрый вариант читается не хуже — используем его всегда.
- Реквизиты ссылок не читаем через точку — только через методы БСП.
- Правила по запросам — в главе [8](./08_queries.md), по вызовам сервера — в главе [9](./09_forms.md).

## Правила

- **15.1** Оптимизация, которая усложняет код, делается только при доказанной — измеренной — необходимости.
- **15.2** Если более быстрый вариант читается не хуже, используется он.
- **15.3** Реквизиты ссылочного значения не читаются через точку. Для этого есть методы БСП:
  - `ОбщегоНазначения.ЗначениеРеквизитаОбъекта()`;
  - `ОбщегоНазначения.ЗначенияРеквизитовОбъекта()`;
  - `ОбщегоНазначения.ЗначениеРеквизитаОбъектов()`;
  - `ОбщегоНазначения.ЗначенияРеквизитовОбъектов()`.

  Описание и пример — на странице [Методы БСП](./bsp_methods.md#чтение-данных-по-ссылке).
- **15.4** Данные, которые нужны много раз, кэшируются — если это оправдано частотой обращений (см. [«Кэширование»](#кэширование)).

<details><summary>Примеры</summary>

Чтение реквизитов ссылки (15.3):

```bsl
// ❌ Плохо: каждое обращение через точку читает из базы весь объект
ИНН = Заказ.Контрагент.ИНН;
КПП = Заказ.Контрагент.КПП;

// ✅ Хорошо: один запрос, только нужные поля
КонтрагентРеквизиты = ОбщегоНазначения.ЗначенияРеквизитовОбъекта(Заказ.Контрагент, "ИНН, КПП");
ИНН = КонтрагентРеквизиты.ИНН;
КПП = КонтрагентРеквизиты.КПП;
```

> `Заказ` здесь — уже прочитанный объект, поэтому `Заказ.Контрагент` — его реквизит, а не обращение через точку к ссылке.

Быстрый вариант, который читается так же (15.2):

```bsl
// ❌ Медленно при многократном поиске: каждый раз полный перебор таблицы
Отбор = Новый Структура("Номенклатура", Номенклатура);
ТоварыСтроки = Товары.НайтиСтроки(Отбор);

// ✅ Читается так же, но поиск идёт по индексу
Товары.Индексы.Добавить("Номенклатура");
// ...
Отбор = Новый Структура("Номенклатура", Номенклатура);
ТоварыСтроки = Товары.НайтиСтроки(Отбор);
```

Настройка, которая читается в каждой строке (15.4):

```bsl
// ❌ Плохо: обращение к базе на каждой из тысяч строк
Для Каждого ТоварыСтрока Из Товары Цикл
	ТоварыСтрока.Округление = Константы.пр_ТочностьОкругления.Получить();
КонецЦикла;

// ✅ Хорошо: значение не зависит от строки — читаем его один раз до цикла
ТочностьОкругления = Константы.пр_ТочностьОкругления.Получить();
Для Каждого ТоварыСтрока Из Товары Цикл
	ТоварыСтрока.Округление = ТочностьОкругления;
КонецЦикла;

// ✅ Хорошо: если настройка нужна многим методам в пределах вызова или сеанса —
// модуль с повторным использованием значений
ТочностьОкругления = пр_НастройкиПовтИсп.ТочностьОкругления();
```

## Пояснения

### Место производительности среди приоритетов

> 🔥 Во имя эффективности совершается больше компьютерных грехов, чем по любой другой причине, включая банальную глупость. *У. Вульф*

Программу нельзя сделать одновременно идеальной и по читаемости, и по скорости. Производительность — лишь одна из сторон качества, и обычно не главная. Скорость работы больше зависит от архитектуры, проектирования метаданных и алгоритмов, чем от оптимизации отдельных строк.

Без замеров у оптимизации гарантирован только один результат — код стал сложнее. Лучшая подготовка к будущей оптимизации — понятный код, который легко изменить.

### Всё в меру

Сравните, сколько времени пользователь думает, вводит данные и отвлекается, и сколько ждёт проведения и записи. Большая часть — время человека.

Но и пренебрегать скоростью нельзя. Лишние 2 секунды при проведении на нагруженной системе: 1000 пользователей × 100 документов в день × 2 секунды — больше 55 часов ожидания в день.

Поэтому:

- сложные «ускоряющие» конструкции (массив структур вместо таблицы значений и т. п.) без необходимости не используются;
- правильно построенный запрос — с параметрами виртуальных таблиц, временными таблицами и индексами — всегда важнее «красоты» его текста;
- быстрый вариант, который читается так же хорошо, используется всегда (15.2).

### Где обычно теряется время

- **Неоптимальные запросы** — см. [чек-лист](./08_queries.md#чек-лист-проверки-запроса).
- **Лишние обращения к СУБД** — данные, которые можно взять из кэша, читаются заново.
- **Контекстные вызовы сервера без необходимости** — см. [9.1](./09_forms.md#91-вызовы-сервера).
- **Обращение через точку к ссылке** — чтение всего объекта ради одного реквизита.
- **Параметры без `Знач`** при вызове сервера — данные возвращаются на клиент.
- **Неочищенная коллекция** уходит на сервер, хотя там её всё равно перезаполнят.
- **Перегруженная форма** — лишние реквизиты и элементы замедляют контекстные вызовы, а замеры кода этого не показывают.

### Кэширование

Кэш полезен, когда данные читаются часто, а хранение обходится дешевле повторного чтения. Если значение нужно раз в 20 минут, хранить его в кэше дороже, чем прочитать заново, — разве что его получение требует тяжёлого расчёта по десяткам таблиц.

**Платформенное кэширование:**

- **общие модули с повторным использованием возвращаемых значений** — значение вычисляется при первом обращении и хранится ограниченное время: на время вызова или сеанса, в зависимости от настройки модуля;
- **`ПредопределенноеЗначение()`** и методы БСП `ОбщегоНазначения.ПредопределенныйЭлемент()`, `ОбщегоНазначенияКлиент.ПредопределенныйЭлемент()` — значение кэшируется после первого получения.

**Собственное кэширование** — сохранение данных в реквизитах формы, переменных модуля, структурах, которые передаются между методами.

> ⚠️ Чем реже обращаются к данным в кэше, тем меньше от него пользы. Часто дешевле прочитать данные из базы напрямую.

### Декомпозиция помогает оптимизации

Небольшие методы с чёткими границами упрощают оптимизацию: ускорив один метод, вы ускоряете всех, кто его вызывает. Большие «хитрые» методы трудно и понять, и ускорить. Но и дробить код на слишком мелкие части не нужно — соблюдайте уровни абстракции и правило «одна операция — один метод».
