# 11. Комментарии и описания

[↑ Оглавление](./README.md)

> Когда комментарий нужен, а когда вреден, и как описывать методы и модули.

**Коротко**

- Лучший комментарий — понятное имя. Комментарий объясняет «почему», а не «что».
- Закомментированного кода и подписей «кто и когда» в своём коде нет: историю хранит хранилище.
- У каждого метода есть описание. У экспортных — полное, по стандарту 1С.

**Термины**

- **Описание** (аннотация) — краткое изложение назначения модуля, метода или переменной модуля. Пишется комментарием перед элементом, вне исполняемого кода.
- **Комментарий** — пояснение внутри исполняемого кода.

## Правила

### 11.1 Комментарии

- **11.1.1** Хорошему коду комментарии почти не нужны. Очевидный код не комментируется — смысл лучше вложить в имена.
- **11.1.2** Вместо комментария — переменная или метод с точным именем.
- **11.1.3** Закомментированный код запрещён. Единственное исключение — изменения типовой конфигурации (см. [13.3](./13_typical_changes.md#133-метки-изменений)).
- **11.1.4** Короткий комментарий пишется в конце строки, которую поясняет. Длинный или относящийся к фрагменту — отдельной строкой перед кодом.
- **11.1.5** Между `//` и текстом — пробел. Исключения: в описаниях методов после `//` допускается табуляция — для выравнивания параметров; закомментированный типовой код (13.3.2) идёт сразу после `//`.
- **11.1.6** Комментарий объясняет «почему», а не «что» и «как».
- **11.1.7** Код, обходящий ошибку платформы или внешней компоненты, обрамляется меткой `[!]` с версией платформы и номером обращения:

  ```bsl
  // [!] Платформа 8.3.XX.XXXX, обращение 12345 ИвановИИ 2026-09-30 {
  // Краткое описание ошибки и обхода
  КодОбхода();
  // } [!] ИвановИИ 2026-09-30
  ```

- **11.1.8** Подписи «кто и когда изменил» в своём коде запрещены — историю хранит хранилище или Git. Подписи допускаются только в метках изменений типового кода (13.3) и в метке `[!]` (11.1.7).
- **11.1.9** TODO допускается только со ссылкой на задачу: `// TODO #12345 Перейти на новый API сервиса`.

### 11.2 Описания

- **11.2.1** У каждого метода есть описание, независимо от `Экспорт`. Исключение — обработчики событий (11.2.7). Описания вставляются [шаблонами текста](../templates/README.md).
- **11.2.2** Экспортные методы, общие модули, переменные модуля приложения и внешнего соединения, экспортные переменные описываются полностью, по [стандарту 1С](https://its.1c.ru/db/v8std/content/453/hdoc): назначение, параметры, возвращаемое значение, при необходимости — пример. По таким описаниям можно автоматически строить документацию — например, инструментом [bsl2jsdoc](https://gitlab.com/shmalevoz/bsl2jsdoc).
- **11.2.3** Небольшому неэкспортному методу с понятным именем и очевидными параметрами хватает одной строки назначения: разделы «Параметры» и «Возвращаемое значение» можно опустить.
- **11.2.4** Если метод изменяет входящие параметры, это сказано в описании (см. [4.2.3](./04_methods.md#42-параметры)).
- **11.2.5** У общего модуля обязательно есть описание: каким объектом управляют его методы.
- **11.2.6** Переменная модуля комментируется в той же строке, после объявления.
- **11.2.7** Обработчики событий — объекта (`ПередЗаписью`), формы (`ПриСозданииНаСервере`), элементов (`КонтрагентПриИзменении`) и команд — отдельного описания не требуют: назначение ясно из имени, параметры описаны в синтакс-помощнике. Отключать для них проверку описания параметров не нужно: BSL Language Server проверяет её только у методов, у которых описание есть. Методы расширений, которые перехватывают типовые методы, описываются по правилу [14.3.4](./14_extensions.md#143-методы).

## Пояснения

### Комментарии не исправляют плохой код

> 🔥 Чаще всего комментарий — признак того, что код не смог объяснить себя сам.

Код меняют, а комментарии забывают. Со временем они перестают соответствовать действительности, и правду говорит только код. Поэтому время лучше потратить на то, чтобы сделать код понятным, а не на комментарий к запутанному.

> ⚠️ Не комментируйте плохой код — перепишите его. *Б. Керниган, Ф. Плоджер*

### Вредные комментарии

- **Шум.** Комментарии «для галочки». Их перестают замечать, а потом они начинают лгать.
- **Пересказ кода.** Не объясняет, не обосновывает и читается не легче самого кода.
- **Устаревшие.** Комментарий остался, а код изменился.
- **Закомментированный код.** «Потом раскомментирую» значит «никогда». Коллеги не решаются его удалить — вдруг важно, — и он копится. Если что-то нужно сделать позже, заведите задачу и напишите TODO со ссылкой.
- **Мёртвые методы.** Метод, который никто не вызывает, — тот же закомментированный код. Удаляйте без сожаления.
- **Сокращения.** Комментарий не должен требовать расшифровки.
- **Журнальные записи.** «Здесь был Вася в прошлую субботу» захламляет код. Для истории есть хранилище и Git.

### Полезные комментарии

- **Основание.** Ссылка на закон, приказ или корпоративный стандарт, из которых следует логика.
- **TODO со ссылкой на задачу.** Если пришлось оставить временное решение, назовите недоработку и заведите задачу.
- **Предупреждение.** Неочевидное поведение, особенность версии платформы, долгое выполнение.
- **Акцент.** Подчёркивает важность детали, которая кажется несущественной.
- **Обоснование отступления.** Если пришлось нарушить стандарт, объясните почему. Это убережёт код от «улучшения» коллегой и покажет, что решение осознанное.

### Описания

> ☝ Хорошее описание не повторяет код, а объясняет его **цель** — на уровень выше, чем код.

Прочитав описание, разработчик понимает, что делает метод, что принимает и что возвращает. Одно предложение на русском читается быстрее двадцати строк кода.

Спрашивайте себя «зачем?», а не «как?». Описание, которое рассказывает, как метод устроен внутри, повторяет код и устаревает вместе с ним. Если внутри хорошо описанного метода всё ещё нужны комментарии, возможно, метод слишком сложный.
