# <img src="./images/09_book_red.svg" align=top height=25 width=25/> 9. Комментарии и аннотации

**Термины.**

* `Аннотация` - Краткое изложение содержания объекта кода (модуль, метод, общая переменная), включающее описание его характеристик. Оформляется лидирующими комментариями вне блоков выполняемого кода.
* `Комментарий` - Пояснения к исходному тексту программы, находящиеся непосредственно внутри комментируемого кода.

## Правила

* **9.1** Написание комментариев не должно отвлекать программиста от написания качественного кода. Качественный код требует достаточно небольшого количества комментариев для описания сложных моментов в коде.
* **9.2** Нет необходимости комментировать очевидные участки кода. Лучше вложить больше смысла в имена переменных и функций, чем их комментировать.
* **9.3** Переменная вместо комментария. Лучше использовать переменную с хорошо подобранным именем, чем обойтись без использования переменной и снабдить текст комментарием.
* **9.4** Программные модули не должны иметь закомментированных фрагментов кода.
* **9.5** Для единообразия комментариев необходимо использовать утвержденные шаблоны текста, размещенными в репозитории проекта
* **9.6** Небольшие комментарии пишутся в конце строки, которую комментируют. Большие комментарии или комментарии к фрагменту кода пишутся перед комментируемым кодом в отдельной строке.
* **9.7** Между символами комментария // и текстом комментария должен быть пробел.
* **9.8** Все экспортные процедуры и функции, общие модули, переменные модуля приложения, модуля внешнего соединения, а также все экспортируемые переменные должны иметь аннотации (лидирующие комментарии с описанием).
* **9.9** Код, который обходит какой-либо глюк (например, платформы или внешней компоненты), необходимо обрамлять комментариями вида:  
  > ```bsl
  > // [!] платформа 8.Х.Х.ХХХХ, обращение 0029738 <ИмяПользователяХранилища> <ТекущаяДата> {
  > Текст исправления ошибки
  > // [!] } <ИмяПользователяХранилища> <ТекущаяДата>
  > ```
* **9.10** Шаблоны комментариев:
  > для ускорения набора текста необходимо пользоваться шаблонами, размещенными в репозитории проекта
  - Начало общего модуля - **в обязательном порядке** должно иметь описание содержимого этого модуля. Должно рассказывать, чем (какие объектом) управляют размещенные в нем методы. *Пример:*
    > ```bsl
    > // Информация о сеансе выполнения
    > // 
    > ...
  - Переменные комментируются после объявляния
    > Перем ДанныеДополнение Экспорт; // Дополнение данных формы
  - Методы должны иметь лидирующее описание вне зависимости от использования `Экспорт`, используя шаблон
    > 
    > ```bsl
    > // <Описание метода
    > //  Продолжение описания метода>
    > // 
    > // Параметры:
    > //    <Имя> - <Тип[, Тип, ...]> [- Описание параметра
    > //    | Продолжение описания параметра]
    > //    <Имя> - <Тип[, Тип, ...]> [- Описание параметра
    > //    | Продолжение описания параметра]
    > //
    > // Возвращаемое значение:
    > //    <Тип[, Тип, ...]> [- Описание возвращаемого значения
    > //    Продолжение описания возвращаемого значения]
    > //
    > // Пример:
    > //    Произвольный текст примера использования
    > //    Продолжение примера
    > ```
    > 
    > *Пример:*
    > 
    > ```bsl
    > // Сравнивает версии. Возвращает 
    > // -1 если Версия1 < Версия2
    > // 0 если Версия1 = Версия2
    > // 1 если Версия1 > Версия2
    > // 	При наличии статуса разработки в какой-либо версии и равенстве вышестоящих
    > // 	частей, версия со статусом разработки считается младшей
    > // 	Если часть строки версии содержит нечисловые символы, то они обрабатываются следующим образом
    > // 		любые символы < (alpha = a) < (beta = b) < rc < # < (pl = p)
    > // 	, нечисловые строки регистроНЕзависимы

    > // Параметры: 
    > // 	Версия1 - Строка - Cтрока версии 1
    > //  | Левый операнд сравнения
    > // 	Версия2 - Строка - Cтрока версии 2
    > //  | Правый операнд сравнения
    > //
    > // Возвращаемое значение:
    > //   Число - Результат сравнения
    > //    При наличии в строках версий  недопустимых символов
    > //    будет вызвано исключение
    > // 
    > // Пример:
    > // ВерсияСравнить("1", "1.0") = -1
    > // ВерсияСравнить("1.0", "1.01") = -1

    > // ВерсияСравнить("1.10", "1.10b") = 1

    > //  
    > Функция ВерсииСравнить(Версия1, Версия2) Экспорт
    >     ...
    > ```
    >
    > По аннотациям экспортных методов, размещенных в областях в областях `Программный интерфейс` в дальнейшем будет строиться документация инструментом [bsl2jsdoc](https://gitlab.com/shmalevoz/bsl2jsdoc)

## Пояснения, рассуждения и рекомендации

### Компенсация плохого кода

> 🔥 В большинстве случаев комментарии – зло.

**В чём проблема?**.

Программисты умеют сопровождать код, но не комментарии. В растущем коде комментарии быстро устаревают, частично или полностью переставая соответствовать ситуации. Только код правдиво сообщает своим содержанием, что он в действительности делает. Лучше потратить время на исправление запутанного кода, чем добавлять к плохому коду комментарии.

Ваш код должен нормально читаться другими программистами.
Проблема не сводится к написанию понятных комментариев. Скорее, вы должны строить код таким образом, чтобы в его структуре проявлялись ваши намерения. Сделать это непросто. Вполне возможно, что это самый сложный навык, которым должен овладеть программист.

**Комментарии не компенсируют плохого кода**.

Одной из распространенных причин для написания комментариев является низкое качество кода. Вы пишете модуль и видите, что код получился запутанным и беспорядочным. Вы знаете, что разобраться в нем невозможно. Поэтому вы говорите себе: «О, да это стоит прокомментировать!» Нет! **Лучше исправьте свой код**!

Грамотное применение комментариев должно компенсировать нашу неудачу в выражении своих мыслей в коде. Обратите внимание на слово «неудачу». Комментарий — часто признак неудачи. Мы вынуждены использовать комментарии, потому что нам не всегда удается выразить свои мысли без них, однако гордиться здесь нечем.

> ⚠️ Не комментируйте плохой код — перепишите его. Брайан У. Керниган и П. Дж. Плауэр

### Вредные комментарии

**Бормотание**.

Не стоит лепить комментарии «на скорую руку» только потому, что вам кажется, что это уместно или этого требует процесс. Если уж вы решаете написать комментарий, не жалейте времени и напишите лучший из всех возможных комментариев.

Такие комментарии часто называют "Шум". Они настолько бесполезны, что мы учимся не обращать на них внимания. В процессе чтения кода наш взгляд просто скользит мимо них. Рано или поздно код вокруг таких комментариев изменяется, и они начинают лгать.

**Избыточные комментарии**.

Как правило это очевидное переписывание кода.

Такой комментарий несет не больше информации, чем программный код. Он не объясняет код, не предоставляет обоснований и не раскрывает намерений. Он читается не проще, чем сам код. Более того, комментарий уступает коду в точности и навязывает читателю эту неточность взамен истинного понимания.  Это избыточные комментарии, вызванные неуместным желанием как-то документировать свои действия.

Задайте себе вопрос: стал ли код понятнее после прочтения комментария? Часто комментарии просто загромождают код и скрывают его смысл, излагая очевидные вещи. Иногда в комментарии включаются описания не относящихся к делу подробностей.

**Профессионал бережет не только свое, но и чужое время, и не отвлекает читающего без повода.**

**Недостоверные комментарии**.

Иногда с самыми лучшими намерениями программист делает в комментариях заявления, неточные и не соответствующие истине. Иногда код переписывается, а комментарий остается без изменений, что вводит в заблуждение еще больше.

**Закомментированный код**.

В программировании редко встречаются привычки более отвратительные, чем закрытие комментариями неиспользуемого кода. Никогда не делайте этого!

«Когда-нибудь в будущем раскомментирую этот код, приведу всё в порядок. Или вдруг эта идея кому-то поможет». Любой закомментированный код только ухудшает ситуацию. Это просто мусор: «потом» равносильно «никогда». Если что-то действительно нужно сделать, создайте краткий TODO-комментарий и задачу.

У других программистов, видящих закомментированный код, не хватает храбрости удалить его. Они полагают, что код оставлен не зря и слишком важен для удаления. В итоге закомментированный код скапливается.

**Закомментированный код - это мусор, которые никогда не будет использоваться. Никогда**.

**Мертвые функции**.

Идентичные по смыслу предыдущему пункту функции и методы, которые не вызываются в программе. Без зазрений совести удаляйте любой код, который не используется во время выполнения программы.

**Сокращения в комментариях**.

Комментарии должны быть однозначны и не заставлять программистов расшифровывать сокращения. Никаких сокращений, кроме самых распространенных, в комментариях быть не должно.

**Журнальные комментарии и ссылки на авторов**.

> ✅ Только при наличии системы контроля версий.

Некоторые программисты добавляют комментарий где указывают, кто и когда внес исправления. Когда-то это было оправдано, но теперь у нас есть системы контроля версий – это гораздо лучший способ обозначить границы зоны ответственности каждого.

Подписи “// Здесь был Вася в прошлую субботу” захламляют код. Не говоря уже о комментариях внутри комментариев, где вообще не понять, кто же из эти комментаторов последним исправлял и является “папой”.

### Полезные комментарии

**Юридические комментарии**.

- Уточнение задачи по какому то юридическому акту или закону вполне уместно.
- Корпоративные стандарты. Ограничьтесь в таком комментарии ссылкой на внешний объект.

**Представление намерений todo**.

Бывает так: нужно было успеть к дедлайну, пришлось писать код быстро, поэтому в нем остались дыры. То есть всё работает, но реализация ущербная. Укажите все недоработки и создайте под них задачи. Каждый комментарий указывает на недоработку или потенциальную уязвимость.

**Предупреждения о последствиях**.

Иногда бывает полезно предупредить других программистов о нежелательных последствиях от каких-либо действий. Возможно неочевидное поведение какой либо версии платформы.

```bsl
// Не запускайте, если только не располагаете
// излишками свободного времени.
```

**Усиление внимания**.

Комментарий может подчеркивать важность обстоятельства, которое на первый взгляд кажется несущественным.

**Обоснование нарушения хорошего стиля**.

Если вы вынуждены нарушить хороший стиль программирования, объясните причину. Благодаря этому программисты, исполненные благих намерений, узнают, что попытка улучшения вашего кода может привести к нарушению его работы, и не станут изменять его. Объяснение ясно скажет, что вы знали, что делаете, а не допустили небрежность — улучшите свою репутацию, если есть такая возможность!

### Аннотации

> ☝ Хорошие аннотации не повторяют код и не объясняют его. Они **поясняют** его **цель**. Аннотации должны объяснять намерения программиста на более высоком уровне абстракции, чем код. И наоборот, аннотации, повторяющие код, на самом деле бесполезны, потому что все уже сказано в самом коде.

**Все экспортные методы из программного интерфейса должны иметь аннотацию**.

**Правило обязательной полезной аннотации**.

- Каждый метод программного интерфейса должен содержать текстовую аннотацию, раскрывающую назначение и особенности эксплуатации метода. Также в аннотации должны быть перечислены и описаны все параметры метода и все варианты возвращаемого значения, если метод технически является функцией. Формат аннотации должен строго соответствовать образцу, приведенному в [стандарте 453](https://its.1c.ru/db/v8std#content:453:hdoc) из системы стандартов и методик фирмы “1С”.
- Исключением могут являться только самые очевидные методы, аннотация которых будет лишней и "высосана из пальца".

Читающий по аннотации должен понимать что выполняет метод. Какие параметры входят в метод и какие есть на выходе. Если входные параметры в процессе выполнения метода меняются - это так же необходимо описать. Гораздо быстрее прочитать одно предложение на обычном языке, чем анализировать 20 строк кода на языке программирования.

**Не все методы обязаны иметь аннотаций**.

Простые (**не экспортные**) методы, состоящие из 5-10 строк точно не требуют аннотации. Её размер превысит размер метода. Цель и алгоритм метода будут высосаны из пальца.

Другая проблема с аннотациями методов состоит в том, что они мешают факторизовать код: затраты, связанные с созданием нового метода, так велики, что программисты будут стремиться создавать меньше методов. Если метод прост и не требует аннотации - то не стоит тратить время на написание аннотации. **Как правило, в таких маленьких методах хорошо сконструированное имя является аннотацией.**

**Отсутствие комментариев**.

Грамотно сконструированный метод при наличии аннотации не требует комментариев внутри себя. Если код требует пояснения внутри метода при наличии аннотации - значит она написана некорректно и требует доработки.

**Задавайте вопрос «Почему?», а не «Как?**.

Аннотации, объясняющие, «как» что то выполняется внутри метода, обычно относятся к уровню языка программирования, а не проблемы. Цель операции почти невозможно выразить в такой аннотации, поэтому она часто оказывается избыточной. В ней, как и в комментарии, появляется шум, пустые слова. Она похожа на политика перед выборами, много слов а смысла нет.
