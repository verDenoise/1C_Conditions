# 4. Методы

[↑ Оглавление](./README.md)

> Как делить код на методы, передавать параметры и возвращать результат.

**Коротко**

- Метод делает одно — то, что написано в его имени — и помещается на экран (40–60 строк).
- Дублирования нет: прежде чем писать, ищем готовое в проекте и БСП.
- У функции один `Возврат` в конце и переменная `Результат`, инициализированная в начале.
- Входящие параметры не изменяем, при вызове сервера передаём их через `Знач`.

## Правила

### 4.1 Декомпозиция

- **4.1.1** Как делить код на методы, продумывается заранее, до того как он написан.
- **4.1.2** Метод делает то и только то, что обозначено в его имени.
- **4.1.3** Дублирование кода запрещено — в том числе дублирование кода коллег. Прежде чем писать, ищем готовую реализацию в проекте и БСП.
- **4.1.4** Длина метода — не больше 40–60 строк, то есть один экран. Исключения нужно обосновать: текст запроса, инициализация коллекции, программное создание элементов формы, условное оформление, действительно неделимый алгоритм.
- **4.1.5** Логические блоки внутри метода разделяются пустой строкой. Если метод длиннее 20 строк не делится на блоки, его стоит переписать. Часто каждый блок лучше вынести в отдельный метод.
- **4.1.6** Логически обособленная часть алгоритма выносится в метод, даже если вызывается один раз или занимает одну строку.
- **4.1.7** В одном выражении — не больше двух уровней вложенных вызовов. Глубже — добавляем промежуточную переменную.
- **4.1.8** Лишних переменных нет. Лишняя — та, что используется один раз, хранит выражение не более чем из двух операндов **и ничего не объясняет своим именем**. Переменная, которая даёт имя «магическому» значению (5.7) или заменяет комментарий (11.1.2), не лишняя.
- **4.1.9** В релизе нет неиспользуемых методов. Интерфейс общего механизма, который пока никто не вызывает, допустим; «мусор» — нет.
- **4.1.10** В коде нет закомментированных фрагментов. Единственное исключение — изменения типового кода (см. [13. Изменение типовой конфигурации](./13_typical_changes.md)).

<details><summary>Примеры к 4.1</summary>

Вложенность вызовов:

```bsl
// ❌ Плохо: три уровня вложенности, выражение читается изнутри наружу
Сумма = пр_Цена.ВВалюту(пр_Цена.СоСкидкой(пр_Номенклатура.ЦенаРозничная(Номенклатура), Скидка), Валюта);

// ✅ Хорошо
ЦенаРозничная = пр_Номенклатура.ЦенаРозничная(Номенклатура);
ЦенаСоСкидкой = пр_Цена.СоСкидкой(ЦенаРозничная, Скидка);
Сумма = пр_Цена.ВВалюту(ЦенаСоСкидкой, Валюта);
```

Лишняя и нелишняя переменная:

```bsl
// ❌ Плохо: переменная ничего не объясняет
ИмяРеквизита = "Склад";
Реквизиты.Добавить(ИмяРеквизита);

// ✅ Хорошо
Реквизиты.Добавить("Склад");

// ✅ Тоже хорошо: используется один раз, но имя объясняет число
ПлатежейВФайлеМаксимум = 1000;
ФайлыПлатежи = пр_ВыгрузкаБанк.ПлатежиРазбить(Платежи, ПлатежейВФайлеМаксимум);
```

Одна строка — тоже повод для метода, если у неё есть смысл:

```bsl
// ❌ Плохо: чтобы понять условие, его приходится разбирать
Если Заказ.Статус = Перечисления.СтатусыЗаказовКлиентов.Согласован
	И Заказ.ДатаОтгрузки <= ТекущаяДатаСеанса() Тогда

	пр_Отгрузка.Создать(Заказ);

КонецЕсли;

// ✅ Хорошо: смысл условия назван
Если пр_ЗаказКлиента.ОтгрузкаДоступна(Заказ) Тогда
	пр_Отгрузка.Создать(Заказ);
КонецЕсли;
```

</details>

### 4.2 Параметры

- **4.2.1** Параметры идут в порядке важности. Параметры со значениями по умолчанию — в конце.
- **4.2.2** Параметры методов, которые вызываются с клиента на сервере, объявляются с `Знач` — тогда изменённые значения не возвращаются на клиент.
- **4.2.3** Изменять входящие параметры, в том числе поля переданных коллекций, нельзя без веской причины (например, передачи кэша). Если метод всё же меняет параметр, это сказано в его описании.
- **4.2.4** Для коллекций, которые возвращает программный интерфейс подсистемы, создаются методы управления их полями: конструктор и методы чтения и установки. Вызывающий код не обращается к ключам структуры напрямую.

<details><summary>Примеры к 4.2</summary>

`Знач` при вызове сервера:

```bsl
// ❌ Плохо: таблица после вызова вернётся с сервера на клиент
&НаСервереБезКонтекста
Функция ЦеныРассчитать(Товары, ВидЦены)

// ✅ Хорошо
&НаСервереБезКонтекста
Функция ЦеныРассчитать(Знач Товары, Знач ВидЦены)
```

Изменение входящих параметров:

```bsl
// ❌ Плохо: функция возвращает итог, но попутно переписывает переданную таблицу
Функция СуммаИтого(Товары)

	Результат = 0;
	Для Каждого ТоварыСтрока Из Товары Цикл
		ТоварыСтрока.Сумма = ТоварыСтрока.Цена * ТоварыСтрока.Количество;
		Результат = Результат + ТоварыСтрока.Сумма;
	КонецЦикла;

	Возврат Результат;

КонецФункции

// ✅ Хорошо: расчёт строк и подсчёт итога — два метода

// Рассчитывает суммы строк товаров.
Процедура СуммыРассчитать(Товары)

	Для Каждого ТоварыСтрока Из Товары Цикл
		ТоварыСтрока.Сумма = ТоварыСтрока.Цена * ТоварыСтрока.Количество;
	КонецЦикла;

КонецПроцедуры

// Итоговая сумма товаров.
Функция СуммаИтого(Товары)

	Результат = Товары.Итог("Сумма");

	Возврат Результат;

КонецФункции
```

Управление полями экспортной коллекции (4.2.4):

```bsl
// Общий модуль пр_ОтправкаПараметры

#Область ПрограммныйИнтерфейс

// Новые параметры отправки письма со значениями по умолчанию.
//
// Возвращаемое значение:
//	Структура - параметры отправки. Поля читаются и устанавливаются методами этого модуля.
//
Функция Создать() Экспорт

	Результат = Новый Структура;
	Результат.Вставить("Важность", ВажностьИнтернетПочтовогоСообщения.Обычная);
	Результат.Вставить("УведомлениеОПрочтении", Ложь);

	Возврат Результат;

КонецФункции

// Важность письма.
//
// Параметры:
//	Параметры - см. Создать
//
// Возвращаемое значение:
//	ВажностьИнтернетПочтовогоСообщения
//
Функция Важность(Параметры) Экспорт

	Результат = Параметры.Важность;

	Возврат Результат;

КонецФункции

// Устанавливает важность письма.
//
// Параметры:
//	Параметры - см. Создать
//	Значение - ВажностьИнтернетПочтовогоСообщения - новое значение.
//
Процедура ВажностьУстановить(Параметры, Значение) Экспорт

	Параметры.Важность = Значение;

КонецПроцедуры

#КонецОбласти
```

```bsl
// Использование
ОтправкаПараметры = пр_ОтправкаПараметры.Создать();
пр_ОтправкаПараметры.ВажностьУстановить(ОтправкаПараметры, ВажностьИнтернетПочтовогоСообщения.Высокая);
пр_Письмо.Отправить(Письмо, ОтправкаПараметры);
```

> Чтение и установка — разные методы: функция только возвращает значение, процедура только меняет (принцип CQRS, см. [Принципы программирования](../articles/principles.md#cqrs--разделение-чтения-и-изменения)). `ВажностьУстановить()` меняет переданную структуру — в этом её назначение, поэтому правило 4.2.3 не нарушено.

</details>

### 4.3 Функции

- **4.3.1** В функции ровно один `Возврат`, и он стоит в конце. Исключение — функции с инструкциями препроцессора, если в скомпилированном коде всё равно остаётся один `Возврат`.
- **4.3.2** Результат функции хранится в переменной `Результат` — или в переменной, чьё имя совпадает по смыслу с назначением функции.
- **4.3.3** Переменная результата инициализируется в начале функции значением по умолчанию.

<details><summary>Примеры к 4.3</summary>

```bsl
// ❌ Плохо: два выхода, а в одной из веток результат не определён
Функция СкидкаПроцент(Клиент)

	Если НЕ ЗначениеЗаполнено(Клиент) Тогда
		Возврат 0;
	КонецЕсли;

	Если пр_Клиент.ПостоянныйЭто(Клиент) Тогда
		Процент = пр_Клиент.СкидкаПостоянная(Клиент);
	КонецЕсли;

	Возврат Процент;

КонецФункции

// ✅ Хорошо: результат задан сразу, выход один

// Процент скидки клиента. Для непостоянных клиентов — 0.
Функция СкидкаПроцент(Клиент)

	Результат = 0;

	Если ЗначениеЗаполнено(Клиент)
		И пр_Клиент.ПостоянныйЭто(Клиент) Тогда

		Результат = пр_Клиент.СкидкаПостоянная(Клиент);

	КонецЕсли;

	Возврат Результат;

КонецФункции
```

</details>

### 4.4 Обработчики событий объектов

- **4.4.1** Обработчики событий записи проверяют `ОбменДанными.Загрузка` и собственные флаги отключения до любых действий и проверок. Сразу решите, что нужно всегда, а что — только при обычной записи, а не при загрузке из обмена.
- **4.4.2** В проекте есть общий механизм отключения проверок в `ПередЗаписью` через ключ дополнительного свойства.
- **4.4.3** Точно так же отключаются действия в `ПриЗаписи` и `ОбработкаПроведения`.

<details><summary>Примеры к 4.4</summary>

```bsl
// Модуль объекта документа пр_ЗаявкаНаЗакупку

// BSLLS:MissingParameterDescription-off - см. синтакс-помощник
Процедура ПередЗаписью(Отказ, РежимЗаписи, РежимПроведения)

	Если ОбменДанными.Загрузка Тогда
		Возврат;
	КонецЕсли;

	Если НЕ пр_ОбъектПроверки.Отключены(ЭтотОбъект) Тогда
		СуммаЛимитПроверить(Отказ);
	КонецЕсли;

	ДокументСуммаРассчитать();

КонецПроцедуры
// BSLLS:MissingParameterDescription-on
```

```bsl
// Общий модуль пр_ОбъектПроверки

// Истина, если для записываемого объекта отключены проверки.
//
// Параметры:
//	Объект - ДокументОбъект, СправочникОбъект - записываемый объект.
//
// Возвращаемое значение:
//	Булево
//
Функция Отключены(Объект) Экспорт

	Результат = Объект.ДополнительныеСвойства.Свойство("пр_ПроверкиОтключены");

	Возврат Результат;

КонецФункции

// Отключает проверки при записи объекта.
//
// Параметры:
//	Объект - ДокументОбъект, СправочникОбъект - записываемый объект.
//
Процедура Отключить(Объект) Экспорт

	Объект.ДополнительныеСвойства.Вставить("пр_ПроверкиОтключены", Истина);

КонецПроцедуры
```

```bsl
// Использование: массовая перезапись без проверок
ЗаявкаОбъект = Заявка.ПолучитьОбъект();
пр_ОбъектПроверки.Отключить(ЗаявкаОбъект);
ЗаявкаОбъект.Записать();
```

> Ранний `Возврат` из процедуры по `ОбменДанными.Загрузка` — обычный приём, так делают и типовые конфигурации. Правило одного `Возврат` (4.3.1) касается функций.

</details>

### 4.5 Прочее

- **4.5.1** Оператор `Перейти` не используется.
- **4.5.2** Используем готовые механизмы: платформу, БСП и то, что уже есть в проекте. Из БСП вызываем только программный интерфейс — служебный может измениться в любом обновлении.
- **4.5.3** Доработка корректно работает под всеми ролями, которые предусматривает бизнес-логика. Проверяем её под пользовательскими правами с учётом RLS, а не только под полными.

## Пояснения

### Почему методы должны быть маленькими

Маленький метод видно целиком, ему легко дать точное имя, его легко проверить. Размер — не самоцель, но если метод не помещается на экран, в нём почти всегда есть самостоятельные части.

**«Слишком просто для отдельного метода»** — главный барьер. Но метод из двух-трёх строк:

- объясняет своим именем, что делают эти строки;
- сохраняет один уровень абстракции в вызывающем коде;
- выручает, когда простая операция со временем усложнится.

> ☝ Вынести фрагмент в метод с хорошим именем — один из лучших способов документировать код.

### Одна операция

**Метод выполняет одну операцию, выполняет её хорошо и больше ничего не делает.**

Признак одной операции — все действия метода находятся **на одном уровне абстракции**. Метод верхнего уровня рассказывает, *что* происходит, методы уровнем ниже — *как*:

```bsl
// ✅ Хорошо: метод читается как описание процесса

// Резервирует товары заказа и уведомляет менеджера.
//
// Параметры:
//	Заказ - ДокументСсылка.ЗаказКлиента - резервируемый заказ.
//
Процедура Выполнить(Заказ) Экспорт

	Товары = ТоварыОстатки(Заказ);
	ТоварыРезервировать(Заказ, Товары);
	МенеджерУведомить(Заказ);

КонецПроцедуры
```

Если в одном методе соседствуют проверка прав, текст запроса, разбор результата и сообщение пользователю, — операций несколько, и метод нужно разделить.

Имя метода — лакмусовая бумажка. Если короткое точное имя не подбирается, метод делает слишком много или его назначение не продумано. Объектный стиль ([2.2](./02_names.md#22-объектный-стиль)) здесь помогает: он даёт однозначный критерий правильности имени и сразу подсказывает, в каком модуле место методу.

### Никаких сюрпризов

Метод делает ровно то, чего читатель ждёт по имени, — без скрытых действий.

```bsl
// ❌ Плохо: что прибавляется — дни, часы? изменится ли переданная дата?
СрокОплаты = ДатуСдвинуть(ДатаДокумента, 5);

// ✅ Хорошо
СрокОплаты = пр_Дата.ДниРабочиеДобавить(ДатаДокумента, 5);
```

Имена вроде `ДанныеОбработать()` или `ВсеВыполнить()` не сообщают ничего. А если код кажется вам «хитрым», для другого он окажется непонятным. **«Хитрый» код — другое название плохого кода**; простое решение есть всегда.

### Признаки проблемного кода

**Спагетти-код** — запутанный код, в котором перемешаны разнородные действия. Он может даже работать правильно и быстро, но читать, отлаживать и менять его почти невозможно: любая доработка заканчивается словами «проще переписать».

Проверьте себя:

- [ ] метод длиной в несколько экранов;
- [ ] вложенность больше трёх уровней, многоэтажные `Если … ИначеЕсли` с циклами внутри;
- [ ] флаги с ничего не говорящими именами (`Флаг2`, `Признак`);
- [ ] условия с двойным отрицанием и цепочками из пяти и более `И`/`ИЛИ`;
- [ ] перемешанные `Попытка` и транзакции, «проглоченные» исключения;
- [ ] метод решает несколько задач, которые делят общие переменные;
- [ ] комментарии, объясняющие, что делает очередной кусок.

Каждый признак сам по себе бывает оправдан. Несколько сразу — повод переписать.

**Код-загадка** написан самым неочевидным способом, но как-то работает. Например, «проверка, что значение — число»:

```bsl
// ❌ Плохо: зачем Попытка? почему -1? почему Null превращается в 0?
Функция ЗначениеЧисло(Значение)

	Результат = -1;
	Попытка
		Результат = ?(Значение = Null, 0, Число(Значение));
	Исключение
		Результат = -1;
	КонецПопытки;

	Возврат Результат;

КонецФункции

// ✅ Хорошо: функция делает ровно то, что написано в имени

// Истина, если значение имеет тип «Число».
Функция ЧислоЭто(Значение)

	Результат = ТипЗнч(Значение) = Тип("Число");

	Возврат Результат;

КонецФункции
```

**Нелогичный код** ставит в тупик даже тогда, когда написан аккуратно:

```bsl
// ❌ Плохо: обработка одновременно «выполнена» и «с ошибками», а что делать пользователю — неясно
Если ОбработкаВыполнена И ОшибкиЕсть = Ложь Тогда
	ПоказатьПредупреждение(, "Обработка выполнена.");
ИначеЕсли ОбработкаВыполнена И ОшибкиЕсть = Истина Тогда
	ПоказатьПредупреждение(, "Обработка выполнена с ошибками!");
Иначе
	ПоказатьПредупреждение(, "При выполнении возникли ошибки!");
КонецЕсли;
```

Режимы, закодированные числами (`ВариантПечати = 0`), — из той же серии: ноль никак не ассоциируется с «предварительным просмотром». Используйте булев флаг (`ПечатьНаПринтер`) или перечисление.

### Параметры

Чем больше параметров, тем сложнее вызывать и тестировать метод.

- Ориентир — не больше трёх основных параметров. Дополнительные передаются структурой четвёртым параметром, и у этой структуры есть конструктор (4.2.4).
- Если параметров больше, скорее всего, они образуют самостоятельный объект со своим именем и модулем.
- Булев параметр-флаг обычно означает, что метод делает две разные вещи. Часто лучше сделать два метода с общим служебным третьим.
- Параметры называются полно: `Ссылка` говорит мало, `ЗаказСсылка` — достаточно.

```bsl
// ❌ Плохо: девять параметров, из них пять булевых флагов
Функция ПисьмоСоздать(Пользователь, Данные = Неопределено, ВложенияПеренести = Ложь,
	Копирование = Ложь, ФорматHTML = Ложь, Дополнительно = Неопределено,
	Владелец = Неопределено, ПодписьДобавить = Ложь, Открыть = Истина) Экспорт

// ✅ Хорошо: основные параметры и структура дополнительных с конструктором
Функция ПисьмоСоздать(Пользователь, Основание, ПисьмоПараметры = Неопределено) Экспорт
```

### Мусор на входе — мусор на выходе

Некорректные входные данные дают некорректный результат, даже если алгоритм верен ([GIGO](https://ru.wikipedia.org/wiki/GIGO)).

- За корректность входных данных отвечает **вызывающий** код. Чтобы его можно было написать правильно, у метода есть исчерпывающее описание параметров.
- Данные из неконтролируемых источников — пользовательский ввод, файлы, внешние сервисы — проверяются на тип и состав там, где они получены.

### Вложенность

Чем глубже вложенность, тем больше условий читателю приходится держать в голове. **Вложенность — не больше трёх уровней**, и три уже говорят об усложнённом коде. Как уменьшить:

- вынести тело цикла или ветки в отдельный метод;
- перенести сложное условие в функцию;
- переставить условия так, чтобы основной вариант обрабатывался первым.

### Простота: KISS и YAGNI

**KISS** (*Keep It Simple, Stupid* — «не усложняй»): если задачу можно решить просто, её решают просто. Принцип не советует, а **запрещает** брать инструменты, алгоритмы и структуры данных сложнее, чем требует задача.

Пример: число нужно превратить в строку из шести символов с ведущими нулями.

```bsl
// ❌ Плохо: «в лоб», ветками
Если Номер < 10 Тогда
	НомерСтрока = "00000" + Формат(Номер, "ЧГ=0");
ИначеЕсли Номер < 100 Тогда
	НомерСтрока = "0000" + Формат(Номер, "ЧГ=0");
// ... и так далее
КонецЕсли;

// ❌ Лучше, но всё равно лишний код
НомерСтрока = Формат(Номер, "ЧГ=0");
Пока СтрДлина(НомерСтрока) < 6 Цикл
	НомерСтрока = "0" + НомерСтрока;
КонецЦикла;

// ✅ Хорошо: это умеет сама платформа
НомерСтрока = Формат(Номер, "ЧЦ=6; ЧВН=; ЧГ=0");
```

**YAGNI** (*You Aren't Gonna Need It* — «вам это не понадобится»): делаем только то, что решает реальную задачу. Функции «на всякий случай» стоят денег при разработке и при сопровождении, а нужны редко. Заказчику нужны не формы и кнопки, а решённая задача; часто он описывает способ решения вместо задачи — и выяснить, что нужно на самом деле, это работа разработчика.

**Оверинжиниринг** — обратная крайность: простую задачу решают самым сложным и «технологичным» способом, с универсальными механизмами и абстракциями «на будущее». Беда не в качестве такого кода, а в цене сопровождения. Типичная история: нужно поменять одну надпись в одной печатной форме, а все формы строятся одним универсальным механизмом через несколько уровней временных таблиц. Поиск занимает часы, а правка меняет надпись сразу везде.

> ⚠️ Оверинжиниринг уничтожает главное преимущество 1С — открытый код, который быстро дорабатывают специалисты средней квалификации.

### Готовое лучше самодельного

Строя дом, никто не собирает холодильник сам. Прежде чем писать сложный метод, проверьте, нет ли готового в платформе, БСП или проекте. Обратная ошибка — принципиально не доверять библиотекам и писать всё вручную: код работает, но обходится дороже, а ручные реализации ещё и расползаются копиями по конфигурации.

### Не уверен — не трогай

> ⚠️ Если что-то в системе кажется странным, ошибочным или лишним, но непонятно, зачем оно такое и что будет после исправления, — не трогайте.

На понимание алгоритма уходит столько времени, сколько нужно, и сэкономить его не получится. Быстрая правка без понимания почти наверняка обернётся исправлением собственных ошибок, и разбираться всё равно придётся.

Пример. Разработчик, принявший систему на сопровождение, решил навести порядок и отсортировал объекты метаданных по алфавиту — включая значения перечислений. После обновления расчёты стали выдавать неверные результаты: одна функция определяла номер месяца по порядковому номеру значения перечисления `Месяцы`. Сортировка превратила январь в август.

**Механизм, который вы не понимаете до конца, не меняют.**
