# 13. Изменение типовой конфигурации

[↑ Оглавление](./README.md)

> Как вносить изменения в конфигурацию на поддержке, чтобы обновления оставались управляемыми.

**Коротко**

- Всё, что можно сделать расширением, делаем расширением. Новые хранимые данные — в конфигурацию.
- Каждое изменение типового кода — в метке `[+]`, `[*]` или `[-]` с задачей, автором и датой.
- Типовые модули не переформатируем, типовые фрагменты не копируем.
- Измерения регистров не меняем никогда.

## Правила

### 13.1 Общие правила

- **13.1.1** Изменений типовых объектов — как можно меньше, и у каждого есть обоснование.
- **13.1.2** Типовой код и типовые реквизиты меняются только в исключительных случаях, и каждое такое изменение отражается в документации проекта.
- **13.1.3** Всё, что можно сделать расширением, делается расширением (см. [14. Расширения](./14_extensions.md)).
- **13.1.4** Новые хранимые данные — объекты и реквизиты — добавляются в конфигурацию.
- **13.1.5** Новые методы размещаются в нетиповых общих модулях. Добавлять методы в типовые общие модули запрещено.
- **13.1.6** Изменённый типовой модуль не переформатируется: не меняем отступы, не добавляем пустые строки. Сравнение конфигураций должно показывать только настоящие изменения. Правила [12. Форматирование](./12_formatting.md) применяются только к коду внутри меток.
- **13.1.7** Копировать большие типовые фрагменты ради небольшой правки запрещено — например, запрос на 20+ строк ради пары строк или форму ради пары элементов. Вместо копии — точечное программное изменение.

<details><summary>Пример к 13.1.7</summary>

```bsl
// ❌ Плохо: типовой запрос скопирован целиком ради одного условия.
// После обновления копия незаметно разойдётся с оригиналом.
Запрос.Текст = "
	|ВЫБРАТЬ
	|	// ... 60 строк, скопированных из типового метода ...
	|ГДЕ
	|	Товары.Склад = &Склад
	|	И НЕ Товары.Номенклатура.пр_ЗапрещенаКПродаже";

// ✅ Хорошо: типовой текст получаем как есть и точечно дополняем условие
ЗапросТекст = ТоварыЗапросТекст();
// [+] #4561 ИвановИИ 2026-09-30 {
ЗапросТекст = пр_ТоварыЗапрос.ПродажаЗапрещеннаяИсключить(ЗапросТекст);
// } #4561 ИвановИИ 2026-09-30
Запрос.Текст = ЗапросТекст;
```

</details>

### 13.2 Типовые хранимые данные

- **13.2.1** Тип значения типового реквизита расширяется только по согласованию с архитектором.
- **13.2.2** Нетиповые поля можно добавлять в: планы обмена, справочники, **шапки** документов, **реквизиты** регистров, отчёты, обработки, планы видов характеристик, планы счетов, планы видов расчёта, бизнес-процессы, задачи.
- **13.2.3** Без прямого согласования с архитектором нельзя менять:
  - состав аналитик табличных частей проводимых документов — особенно если он влияет на уникальность выборок для движений;
  - состав ресурсов регистров.
- **13.2.4** Состав измерений регистров не меняется никогда.

### 13.3 Метки изменений

- **13.3.1** Каждое изменение типового кода обрамляется меткой с номером задачи, именем пользователя хранилища и датой. Закрывающая метка повторяет задачу, пользователя и дату — так парные метки легко найти поиском. Метки вставляются [шаблонами текста](../templates/README.md).
- **13.3.2** Изменённый или удалённый типовой код не удаляется, а остаётся закомментированным внутри метки. Это единственный случай, когда закомментированный код разрешён. Он комментируется стандартной командой конфигуратора (`//` без пробела), чтобы его было легко отличить от поясняющих комментариев.

| Метка | Когда |
|---|---|
| `[+]` | код добавлен |
| `[*]` | код изменён: исходный закомментирован, новый добавлен |
| `[-]` | код удалён: исходный закомментирован |

<details><summary>Примеры к 13.3</summary>

Добавление:

```bsl
// [+] #4521 ИвановИИ 2026-09-30 {
// Заполнение склада по умолчанию из настроек пользователя
пр_ЗаказКлиента.СкладПоУмолчаниюЗаполнить(ЭтотОбъект);
// } #4521 ИвановИИ 2026-09-30
```

Изменение:

```bsl
// [*] #4530 ИвановИИ 2026-09-30 {
// Цена берётся с учётом соглашения клиента
//Цена = ЦенообразованиеСервер.ЦенаНоменклатуры(Номенклатура, ВидЦены, Дата);
Цена = пр_Цена.ПоСоглашению(Номенклатура, Соглашение, Дата);
// } #4530 ИвановИИ 2026-09-30
```

Удаление:

```bsl
// [-] #4544 ИвановИИ 2026-09-30 {
// Проверка лимита перенесена в пр_ЗаказКлиентаЛимит
//ЛимитПроверить(Отказ);
// } #4544 ИвановИИ 2026-09-30
```

</details>

## Пояснения

### Зачем в типовом коде подписи и закомментированный код

В своём коде подписи «кто и когда» и закомментированный код запрещены: историю хранит хранилище или Git. С типовым кодом иначе. При обновлении разработчик сравнивает и объединяет модули, и история хранилища в этот момент не поможет: прямо в тексте нужно видеть, что здесь наша доработка, зачем и по какой задаче она сделана и как выглядел исходный код. Метки дают ровно это.

### «Минимум изменений» — не единственный критерий

Трудоёмкость обновлений зависит не только от числа изменений. Их должно быть мало, чтобы при обновлении переносить меньше. Но перенос должен быть ещё и надёжным, а изменения — легко находиться при сравнении и объединении. Поэтому скопированный целиком типовой запрос с правкой в двух строках хуже двух точечных программных правок: копия при обновлении незаметно разойдётся с оригиналом.
