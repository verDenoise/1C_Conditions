# 15. Производительность

Правила, влияющие на производительность, собраны в профильных главах:

- вызовы сервера и формы — [9. Формы и клиент-серверное взаимодействие](./09_forms.md);
- запросы и чек-лист их проверки — [8. Запросы](./08_queries.md).

Здесь — общий подход и типичные причины медленной работы.

## Правила

- **15.1** Оптимизация, которая усложняет код, выполняется только при доказанной (измеренной) необходимости.
- **15.2** Если более быстрый вариант ничуть не хуже читается, используется именно он.
- **15.3** Обращение через точку к реквизитам ссылочного значения запрещено. Для чтения реквизитов используются методы БСП:
  - `ОбщегоНазначения.ЗначениеРеквизитаОбъекта()`;
  - `ОбщегоНазначения.ЗначенияРеквизитовОбъекта()`;
  - `ОбщегоНазначения.ЗначениеРеквизитаОбъектов()`;
  - `ОбщегоНазначения.ЗначенияРеквизитовОбъектов()`.
- **15.4** Повторно используемые данные кэшируются, если это оправдано частотой обращений (см. «Кэширование» ниже).

<details><summary>Примеры</summary>

Обращение через точку:

```bsl
// ❌ Плохо: каждое обращение через точку читает из базы весь объект
ИНН = Заказ.Контрагент.ИНН;
КПП = Заказ.Контрагент.КПП;

// ✅ Хорошо: один запрос, только нужные поля
КонтрагентРеквизиты = ОбщегоНазначения.ЗначенияРеквизитовОбъекта(Заказ.Контрагент, "ИНН, КПП");
ИНН = КонтрагентРеквизиты.ИНН;
КПП = КонтрагентРеквизиты.КПП;
```

> `Заказ.Контрагент` здесь — реквизит уже прочитанного объекта `Заказ`, а не обращение через точку к ссылке.

Быстрый вариант, не ухудшающий читаемость (правило 15.2):

```bsl
// ❌ Медленно при многократном поиске: каждый раз полный перебор таблицы
Отбор = Новый Структура("Номенклатура", Номенклатура);
ТоварыСтроки = Товары.НайтиСтроки(Отбор);

// ✅ Читается так же, но поиск идёт по индексу
Товары.Индексы.Добавить("Номенклатура");
// ...
Отбор = Новый Структура("Номенклатура", Номенклатура);
ТоварыСтроки = Товары.НайтиСтроки(Отбор);
```

## Пояснения и рекомендации

### Приоритет производительности

> 🔥 Во имя эффективности совершается больше компьютерных грехов, чем по любой другой причине, включая банальную глупость. *(У. Вульф)*

Программу нельзя сделать одновременно идеальной и по читаемости, и по производительности. Производительность — лишь один из аспектов качества, и, как правило, не самый важный. Скорость работы в большей степени зависит от архитектуры, проектирования метаданных и алгоритмов, чем от оптимизации отдельных строк кода.

Единственный результат оптимизации без замеров, в котором можно быть уверенным, — код стал сложнее. Лучшая подготовка к будущей оптимизации — ясный код, который легко изменить.

### Всё в меру

Сравните время, которое пользователь тратит на обдумывание, ввод данных и паузы, со временем, которое занимает проведение и запись. Бо́льшая часть — время человека.

Но и пренебрегать производительностью нельзя. Лишние 2 секунды при проведении на нагруженной системе: 1000 пользователей × 100 документов в день × 2 секунды — это больше 55 часов суммарного ожидания в день.

Поэтому:

- сложные для чтения «ускоряющие» конструкции (массив структур вместо таблицы значений и т. п.) без необходимости не используются;
- правильно построенный запрос — с параметрами виртуальных таблиц, временными таблицами и индексами по полям соединений — всегда важнее «красоты» текста запроса;
- если быстрый вариант читается так же хорошо, он используется всегда (правило 15.2).

### Типичные причины медленной работы

- **Неоптимальные запросы.** См. [чек-лист](./08_queries.md#чек-лист-проверки-запроса).
- **Лишние обращения к СУБД.** Данные, которые можно взять из кэша (платформенного или своего), читаются из базы заново.
- **Контекстные вызовы сервера без необходимости.** См. [9.1](./09_forms.md#91-вызовы-сервера).
- **Обращение через точку к ссылке.** Читает весь объект ради одного реквизита.
- **Параметры без `Знач`** при вызове сервера: данные гоняются обратно на клиент.
- **Большая коллекция уходит на сервер неочищенной**, хотя там её всё равно перезаполнят.
- **Перегруженная форма.** Лишние реквизиты и элементы замедляют контекстные вызовы, причём замеры времени кода это показывают не всегда.

### Кэширование

Кэш полезен, когда данные читаются часто, а хранение обходится дешевле повторного чтения. Если данные нужны раз в 20 минут, хранить их в кэше дороже, чем прочитать заново, — если только их получение не требует тяжёлого расчёта по десяткам таблиц.

**Платформенное кэширование:**

- **общие модули с повторным использованием возвращаемых значений** — значение вычисляется при первом обращении и хранится ограниченное время (на время вызова или сеанса — по настройке модуля);
- **`ПредопределенноеЗначение()`** и методы БСП `ОбщегоНазначения.ПредопределенныйЭлемент()`, `ОбщегоНазначенияКлиент.ПредопределенныйЭлемент()` — значение кэшируется после первого получения.

**Собственное кэширование** — сохранение данных в реквизитах формы, переменных модуля, структурах, передаваемых между методами.

> ⚠️ Чем реже обращаются к кэшированным данным, тем меньше от кэша пользы. Часто дешевле получить данные из базы напрямую.

### Декомпозиция помогает оптимизации

Небольшие методы с чёткими границами упрощают оптимизацию: улучшив один метод, вы ускоряете всех, кто его вызывает. Большие «хитрые» методы трудно и понять, и оптимизировать. Но не дробите код на слишком мелкие части — соблюдайте уровни абстракции и правило «одна операция — один метод».
