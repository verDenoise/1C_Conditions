## Правила

### 6.1 Условные операторы и циклы

* **6.1.1** Строго говоря, любой условный оператор усложняет блок кода в два раза. Поэтому количество ветвлений кода должно быть минимально. Итоговая цикломатическая сложность метода не должна превышать 10, в отдельных случаях 15. Большие значения сложности обязательно должны сопровождаться комментарием относительно причин.
* **6.1.2** Следует размещать основной вариант после Если, а не после Иначе. Пишите код так, чтобы нормальный путь выполнения был очевиден.
* **6.1.3** Варианты ИначеЕсли должны располагаться должны идти в порядке вероятности выполнения условия, более вероятные должны стоять выше. Исключением могут быть случаи проверок по значениям перечисления или предопределенных значений справочник, в общем случае любое законченное множество.
* **6.1.4** Следует упрощать сложные условия в Если с помощью вызова логических функций. В дополнение к [4.1.3](./code_standart_04_methods.md#41-%D1%81%D1%82%D1%80%D1%83%D0%BA%D1%82%D1%83%D1%80%D0%BD%D0%BE%D0%B5-%D0%BE%D1%84%D0%BE%D1%80%D0%BC%D0%BB%D0%B5%D0%BD%D0%B8%D0%B5-%D0%BA%D0%BE%D0%B4%D0%B0) - если условие может быть использовано более одного раза, то его следует разместить в отдельном методе.
* **6.1.5** Следует избегать запутанных цепочек условных операторов. Если цепочка необходима, скорее всего, её можно выделить в отдельный метод.
  > Исключение из правила - тернарные операторы. Разница в производительности между оператором ? и условием Если может составлять на различных платформах до 7% (семи процентов) в пользу оператора ?
* **6.1.7** Необходимо при помощи скобок в явном виде задавать порядок выполнения сложных логических конструкций.

### 6.2 Попытка-Исключение

* **6.2.1** Нужно использовать исключения для передачи наверх сообщений с одновременным прекращением выполнения фрагмента кода. Исключения могут быть иерархическими, поэтому объект, вызывающий исключение, должен в текст ошибки добавлять данные, по которым пользователь сможет понять, откуда возникла ошибка. При обработке возникшего исключения обязательно должно быть либо выдано сообщение, либо вызвано исключение. Вызов исключений оператором ВызватьИсключение без текста допускается только в случае предварительной выдачи сообщения, это обычно применяется для привязки сообщения к конкретному реквизиту формы.
* **6.2.2** Использовать `Попытку-Исключение-КонецПопытки` нужно только в тех случаях, когда высока вероятность ошибки по причинам не зависящим от качества кода (обращение к файлам, внешним источникам данных, обработка данных, структура которых не гарантировано правильная и т.п.)
* После `Исключение` сразу должен выполняться оператор `Информация = ИнформацияОбОшибке();` или какой-либо общий метод получения информации об ошибке. Это, в частности, упростит отладку.
* **6.2.3** Блок `Исключение` должен в любом случае содержать либо выдачу сообщения пользователю или передачу исключения "наверх" через `ВызватьИсключения`
* **6.2.4** Не следует использовать функцию `ОписаниеОшибки()` для вывода сообщений об ошибке. Предпочтительней использовать `ПодробноеПредставлениеОшибки(ИнформацияОбОшибке())`, если пишем в ЖР Или `КраткоеПредставлениеОшибки(ИнформацияОбОшибке())` если информация выводится пользователю.

### 6.3 Транзакции

* **6.3.1** Транзакции следует использовать с учетом того,  что 1С поддерживает вложенные транзакции только на уровне выполнения кода, но не на уровне базы данных. Это означает, что для отсутствия ошибок времени выполнения на каждое `НачатьТранзакцию()` должно быть не больше одного `ОтменитьТранзакцию()` или `ЗафиксироватьТранзакцию()` на каждый вариант выполнения кода. Для успешной фиксации транзакции все вложенные `НачатьТранзакцию()` должны быть закрыты через `ЗафиксироватьТранзакцию()`. Для отмены всех вложенных транзакций достаточно одного `ОтменитьТранзакцию()` на любом уровне вложенности, при этом все последующие `ОтменитьТранзакцию()` и `ЗафиксироватьТранзакцию()` выполняются без ошибок, но реально ничего не делают, соответственно в этом случае они необязательны. Метод `ТранзакцияАктивна()` возвращает Истина до тех пор, пока все вложенные `НачатьТранзакцию()` не будут закрыты через `ОтменитьТранзакцию()` или `ЗафиксироватьТранзакцию()`.
* **6.3.2** Начало и завершение транзакции **обязательно** должны располагаться в одном методе.
* **6.3.3** При записи объектов необходимо использовать транзакцию в явном виде с использованием попытки. Завершающим оператором попытки должен быть `ЗафиксироватьТранзакцию()`, блок исключения вторым оператором должен содержать `ОтменитьТранзакцию()`. *Пример:*
  > <details><summary>Развернуть</summary>
  > ```bsl
  > НачатьТранзакцию();
  > ...
  > Попытка
  >     Объект.Записать();
  >     ЗафиксироватьТранзакцию();
  > Исключение
  >     Информация = ИнформацияОбОшибке();
  >     ОтменитьТранзакцию();
  >     ВызватьИсключение НСтр("ru = 'При записи справочника произошла ошибка! Обратитесь к разработчикам.'");
  > КонецПопытки;
  > ```
  > </details>
* **6.3.4** Транзакции, начатые самой платформой (например, при записи объекта), следует отменять только через выставление параметра Отказ в Истина соответствующего обработчика.
* **6.3.5** сли внутри транзакции при выполнении обращения к базе данных произошла ошибка, то любое последующее обращение к базе данных будет вызывать ошибку "В данной транзакции уже происходили ошибки" до тех пор, пока не будет вызван метод `ОтменитьТранзакцию()`, поэтому к примеру для вывода сообщений считывание информации о реквизитах объекта, вызвавшего ошибку, следует делать либо заранее, либо после вызова этого метода.

## Пояснения, рассуждения и рекомендации

### Циклы

**Делайте длинные циклы особенно ясными**.

**Длина увеличивает сложность.** Если вы пишете короткий цикл, вы можете использовать более рискованные управляющие структуры, такие как "Прервать" и "Продолжить", множественные выходы, сложные условия завершения и т.д. Если вы пишете более длинный цикл и проявляете хоть какую то заботу о читателях, вы предусмотрите в цикле только один выход и сделаете условие выхода исключительно понятным.

**Делайте циклы достаточно короткими**, чтобы их можно было увидеть сразу целиком. Выделяйте внутреннюю часть длинных циклов в отдельные методы. Если цикл хорошо спроектирован, то код внутри него часто можно выделить в один или несколько методов, которые будут вызываться из цикла.

> ☝ Когда вы оцените преимущество создания простого кода, вы редко будете писать циклы длиннее 15 - 20 строк.

**Вложенность**.

Ограничивайте вложенность тремя уровнями. Исследования показали, что способность программистов разобраться в цикле существенно снижается, если уровень вложенности превышает три уровня. 

Если вам нужно большее число уровней, сделайте цикл короче (концептуально), вынеся его часть в отдельный метод или упростив управляющую структуру.

**Вложенные циклы**.

Смысловые имена индексов коллекций одновременно уточняют и назначение цикла, и элемент коллекции, к которому вы планируете обратиться.

**Прерывания цикла**.

> ☝ Остерегайтесь цикла с множеством операторов "Прервать", разбросанных по всему коду

Применение "Прервать" заставляет читателя смотреть внутрь цикла, чтобы разобраться в его управлении. Это усложняет понимание цикла. Цикл, содержащий большое количество операторов "Прервать", может сигнализировать о нечетком представлении структуры цикла или его роли в окружающем коде. 

Рост числа "Прервать" увеличивает вероятность, что цикл может быть более ясно представлен в виде набора нескольких циклов вместо одного цикла с множеством выходов.

**Служебные операции**.

Располагайте служебные операции либо в начале, либо в конце цикла.

Служебные операции цикла (это выражения вроде Индекс = Индекс + 1, "Прервать", "Продолжить", "Возврат" и иные.), чье основное назначение не выполнять работу в цикле, а управлять циклом. 

В случае расположения таких конструкций в середине их сложнее заметить, понять логику и исправить без неочевидных последствий.

## Условные операторы

**Нормальный вариант после `Если`, а не после `Иначе`**.

Пишите код так, чтобы нормальный вариант развития событий обрабатывался в первую очередь. Это совпадает с главным принципом размещения действий, являющихся результатом выбора, как можно ближе к точке этого выбора.

Такой подход позволяет фокусировать чтение в основном направлении, а не преодолевать исключительные ситуации, поэтому этот код в целом читабельнее. Стек ошибочных условий, расположенный внизу условия, — признак хорошо написанного кода обработки ошибок.

**Осмысленные выражения после оператора `Если`**.

Иногда можно встретить код, в котором блок `Если` пуст. Опытные программисты не станут писать такой код хотя бы затем, чтобы избежать лишней работы по вводу пустой строки и оператора "Иначе". Этот код выглядит глупо и может быть легко улучшен путем отрицания предиката в выражении "Если", перемещения кода из блока "Иначе" в блок "Если" и удаления блока "Иначе". *Например*:

```bsl
// Выводит сообщение об ошибке заполнения поля 
// 
Процедура СообщитьОбОшибке(ОбъектСОшибкой, ТекстОшибки, Поле = Неопределено, ИмяТабличнойЧасти = Неопределено, НомерСтроки = Неопределено, МассивСообщений = Неопределено) Экспорт

    Сообщение = Новый СообщениеПользователю();
    Сообщение.Текст = ТекстСообщения;

    Если НЕ ОбщегоНазначения.ИнформационнаяБазаФайловая() Тогда
        // Платформа 8.2.15
    Иначе
        Если ИмяТабличнойЧасти <> Неопределено Тогда
            Сообщение.Поле = ИмяТабличнойЧасти + "[" + (НомерСтроки - 1) + "]." + Поле;
        ИначеЕсли ЗначениеЗаполнено(Поле) Тогда
            Сообщение.Поле = Поле;
        КонецЕсли;

        Сообщение.УстановитьДанные(ОбъектСОшибкой);
    КонецЕсли;

    Сообщение.Сообщить();

    Отказ = Истина;

    // Розница.ОтрицательныеОстатки
    Если МассивСообщений <> Неопределено Тогда
        МассивСообщений.Добавить(Новый Структура("Текст, Поле", Сообщение.Текст, Сообщение.Поле));
    КонецЕсли;

КонецПроцедуры // СообщитьОбОшибке()
```

**Сложные проверки**.

Упрощайте сложные проверки с помощью вызовов логических функций или отдельных переменных, обозначенных заранее.

Разбивайте сложные проверки на части с помощью новых логических переменных. Вместо создания чудовищных условий с множеством элементов присвойте значения этих элементов промежуточным переменным, что позволит выполнять упрощенную проверку.

**Размещайте сложные выражения в логических функциях.** Если какая то проверка выполняется неоднократно или отвлекает от основного хода алгоритма программы, поместите ее код в отдельную функцию и проверяйте значение этой функции. Если выражение достаточно сложное, этот вид рефакторинга повысит удобочитаемость кода. Если выражение используется более одного раза, он исключит необходимость внесения параллельных изменений и снизит вероятность ошибок.

Если вы проверяете условие только раз, вам может показаться, что его не стоит помещать в отдельный метод. Но вынесение условия в отдельную, хорошо названную функцию улучшит читабельность кода и упростит понимание того, что этот код делает. Это достаточная причина для создания функции. Имя нового метода привносит в программу абстракцию, которая документирует назначение проверки прямо в коде. Это даже лучше, чем документирование условия с помощью комментариев, потому что код будет читаться и модифицироваться с большей вероятностью, чем комментарии.

**Плохой пример**:

```bsl
Если ((ТекДанные.ТипДоговора = ТипАгент И ТекДанные.ЭтоФорма2 = Истина И ПравильныйРСО.Получить(ТекДанные.РСО) <> Неопределено) ИЛИ (ТекДанные.ТипДоговора = ТипМодель И ТекДанные.ВидУслуги = Перечисления.ТипыЖКУ.Жилищное И ТекДанные.ДатаЗавершения <= КонецМесяца(ДатаОбработки)) И ТекДанные.Статус = Перечисления.СтатусДоговора.Действует И ПлохиеУК.Получить(ТекДанные.ВтораяСторона) = Неопределено) Тогда
```

> 👉 Всегда стоит предполагать, что код будет обслуживать человек, не обладающий редкой способностью разобрать столь запутанные условия. Такие условия требуют декомпозиции. Стоит поменять какое либо "И" на "ИЛИ" и результат будет абсолютно непредсказуем.

**Простые условия**.

- Тернарный оператор для простых конструкций.

```bsl
// Плохо
Если НДС0 Тогда
    Возврат 0;
Иначе
    Возврат 18;
КонецЕсли;

// Хорошо
Возврат ?(НДС0, 0, 18);
```

**Сокращение простые логические конструкций**.

```bsl
// Трудно прочитать
Если ПроверкаПройдена ИЛИ ОтключитьБизнесЛогику() Тогда
    РазрешеноПроведение = Истина;
Иначе
    РазрешеноПроведение = Ложь;
КонецЕсли;

// Легче прочитать
РазрешеноПроведение = ПроверкаПройдена ИЛИ ОтключитьБизнесЛогику();
```

**Используйте неявное сравнение логических величин с Истина или Ложь**.

Использование неявных сравнений уменьшает число элементов, которые придется помнить при чтении кода, и приближает получаемое выражение к разговорному языку.

**Использование скобок**.

Если у вас есть сложное логическое выражение, не надейтесь на порядок вычисления его операндов - используйте скобки, чтобы сделать ваши намерения понятными. Скобки уменьшают требования, предъявляемые к читателю кода, который может и не разобраться в тонкостях вычисления логических выражений. Если вы благоразумны, то не будете полагаться на собственную или чью то еще способность правильно запомнить приоритет вычислений.

Однако если вы составили такое условие, которое требует указания скобок для лучшего понимания, возможно стоит упростить такую сложную проверку.

**Старайтесь избегать отрицательных условий**.

В ситуациях, когда для условных ветвлений в коде задействуются переменные-флаги (или методы-флаги), во всем коде необходимо использовать единый стиль: все флаги должны быть либо утверждающими, либо отрицающими. **При прочих равных, безусловный приоритет следует отдавать стилю утверждающих флагов.**

```bsl
Если ПроведениеРазрешено Тогда
```

предпочтительнее записи

```bsl
Если НЕ ПроведениеРазрешено Тогда
```

Стоит избегать отрицания отрицания, как тут например:

```bsl
// Какое именно условие здесь описано, читателю предлагается разобрать самостоятельно
// Сон разума, пост сдал.

Если НЕ (НеХватаетТовара ИЛИ НЕ КонтрольОстатковНнОтключен ИЛИ НеХватаетТовара И КонтрольОстатковНеОтключен) Тогда
```

**Порядок вычислений**.

Если порядок вычисления нескольких условий не имеет значения полезнее ставить простые условия в начало, что бы они выполнялись в первую очередь.

## Попытки и исключения

> 📌 [Стандарт ИТС](https://its.1c.ru/db/v8std/content/499/hdoc)

Существует простое правило - **если есть возможность отказаться от попытки и обойтись без нее - это необходимо сделать**. Увеличение количества попыток в коде усложняет отладку, читаемость кода, а так же затрудняет поиск действительно значимых исключений выполнения кода.

**Механику исключений платформы необходимо использовать строго по прямому назначению, то есть для попыток выполнить небезопасный код таким образом, чтобы получить возможность обработать ошибку**.

Неудачное использование попыток:

**Не допускается** использование исключений для проверки типа или корректности значения переменных, не допускается использование исключений в качестве замены условным ветвлением кода.

```bsl
Попытка
    Количество = СтруктураРезультата.Количество;
    РассчитатьКоличествоВСтроке(Количество);
Исключение
    ЗаполнитьКоличествоПоУмолчанию();
КонецПопытки;
```

**Не допускается** делать проверки наличия у объекта реквизитов, методов, макетов и т.п., используя для этого исключения.

```bsl
Попытка 
    КонтекстЭДОСервер.ПолучитьМакет("КомпонентаОбмена");
    ПутьВК = КонтекстЭДОСервер.ПутьКОбъекту + ".Макет.КомпонентаОбмена";
Исключение
КонецПопытки;

// Или
Попытка
    Организация = Объект.Организация;
Исключение
    Организация = Справочник.Организации.ОсновнаяОрганизация();
КонецПопытки;
```

**Не допускается** использовать исключения для приведения значения к типу.

```bsl
Попытка
    КоличествоДнейРазрешения = Число(Значение);
Исключение
    КоличествоДнейРазрешения = 0;
КонецПопытки;
```

<u><b>Не допускается ни при каких обстоятельствах</b></u> “проглатывание” исключения, то есть использование оператора Попытка с пустым или не функциональным блоком "Исключение". *Примеры*:

```bsl
Попытка
    ПеременнаяТекст = ЭтаФорма[ИмяРеквизитаПоляОтображенияСодержания];
Исключение

КонецПопытки;

// Тоже нельзя
Попытка
    ПеременнаяТекст = ЭтаФорма[ИмяРеквизитаПоляОтображенияСодержания];
Исключение
    ЗаписьЖерналаРегистрации("Ошибка инициализации формы", УровеньЖерналаРегистрации.Ошибка);
КонецПопытки;
```

> 🔥 Одно только наличие записи ошибки в журнал регистрации практически всегда можно приравнять к **отсутствию** какого либо обработчика в секции `Исключение`. Журнал не читается оперативно, а иногда и вовсе не читается. Ключевые ошибки желательно выводить сразу.

## Прочие конструкции

**Множественные возвраты из метода**.

Минимизируйте число возвратов из каждого метода.

Тяжело понять логику метода, если при чтении его последних строк вы не подозреваете о возможности выхода из него где то вверху. По этой причине используйте операторы возврата благоразумно — только если они улучшают читабельность.

**Правило кластерного индекса**.

- Везде, где каким-либо образом задействован перечень строковых величин, они должны располагаться в алфавитном порядке.
- Если что-то внутри кода можно отсортировать по алфавиту, необходимо сразу добавлять новый элемент в правильное место.

> 👉 Простым примером правила может служить создание структуры с помощью конструктора, ключи у которой должны идти в алфавитном порядке.
